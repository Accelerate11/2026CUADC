# CUADC：CUAV＋ArduCopter 飞控配置、调参、数传与RTK完整教程

> 从零建立可验证的飞行系统；重点讲内置AutoTune与官方Lua悬停QuickTune。

**版本：1.0｜资料核对：2026-09-05｜适用任务：多旋翼无人机侦察与救援。**

本教程面向第一次接触CUAV与ArduCopter的队员，也供已经会起飞、但尚不熟悉参数、日志和自动整定的成员查阅。主线是：**硬件和供电正确→静态配置与传感器可信→通信和导航可靠→机械/滤波健康→自动整定→载荷及速度包络→全任务和失效验收。**

## 1. 调飞控的目标：让任务有可靠的物理执行基础

CUADC 多旋翼侦察与救援不是单纯“飞机能悬停”。一架能完成任务的飞机，要先后满足几种不同要求：满载起飞、较快转场、低速搜索、低空收敛、静稳投放、载荷突变后恢复、侦察、返航和准确降落。不同环节约束的是不同子系统。

**飞控整定的任务是让实际运动可靠地跟踪合理的指令，不是把不合理指令变成合理指令。**

| 现象 | 首先检查的层级 | 不应该先做的事 |
|---|---|---|
| 一解锁就侧翻 | 电机顺序、旋向、桨型、机架类型、姿态方向 | 运行 AutoTune |
| 图像桶坐标整体偏一侧 | 相机外参、坐标约定、航向、时间延迟 | 增大横滚 P |
| 平稳但悬停位置缓慢漂移 | GNSS/EKF/航向、外环、风、定位基准 | 直接增加 D |
| 高速到点后冲过目标 | 制动距离、轨迹限加速度、实际速度 | 只缩小航点半径 |
| 舵机 ACK 成功但瓶子未掉 | 供电、机构卡滞、行程、载荷反馈 | 再调姿态环 |
| 一投掉水瓶高度上冲 | 推力余量、重量变化、垂向控制、动作时序 | 把全部增益统一加倍 |

整个教程按“先能正确感知，再能稳定控制，最后能可靠执行任务”的顺序组织。算法名不是验收结果；要用日志、重复试飞和明确的失效处理证明改动有效。[S01](#s01)[S02](#s02)

## 2. 零基础先认识这些名词

**飞控硬件**是 CUAV 的电路板、传感器和接口；**ArduCopter 固件**是运行在板上的程序；**Mission Planner** 是地面站；**MAVLink** 是通信协议；**MAVROS** 是 ROS 与 MAVLink 之间的接口组件。它们不是同一件东西。

**IMU** 提供角速度和比力。陀螺仪不直接告诉飞机“现在位于哪里”；加速度计读数也不等于经过地球坐标变换、减去重力后的运动加速度。

**AHRS/EKF** 把 IMU、磁力计、气压计、GNSS 等信息组合成姿态、速度、位置估计。**RTK** 改善卫星定位解，不是独立的飞行控制器。**GPS for Yaw** 使用天线基线提供航向，又是另一种功能。

**P、I、D、FF** 是控制器中的比例、积分、微分和前馈项。**滤波器**用于处理噪声，但会引入动态影响；滤得越狠不一定越稳定。

**解锁 armed** 代表飞控允许动力系统进入工作状态。**安全按钮 safety switch**、**电机紧急停止 emergency stop**、**飞行模式切换**和**物理断电**不是同一种保护。

**RC 输入通道**表示接收机上送的控制信息；**SERVO 输出通道**表示飞控向电机/舵机输出的功能。`RC9_OPTION` 与 `SERVO9_FUNCTION` 没有天然的一对一关系。

**AutoTune** 是自动整定机制；**AUTO** 是执行机载任务的飞行模式；**GUIDED** 是接受外部目标指令的模式。你们 v11 主要走 GUIDED，不是把整条任务上传成 AUTO 航点。[S03](#s03)[S04](#s04)[P1](#p1)

## 3. 把你们的任务要求翻译成飞控验收项目

【源码事实】上传的 v11 在 RELEASE 前要求水平速度不超过 0.15 m/s、垂直速度绝对值不超过 0.10 m/s、横滚和俯仰**各自**不超过 8°、角速度向量模长不超过 10°/s，并连续满足 0.50 s。它还检查目标身份、区域、高度和投放口位置。[P1](#p1)

这些是状态机判断门限，不是已经测得的飞机性能，也不是 ArduCopter PID 参数。

由此可以设计任务相关测试：固定目标点附近能否重复进入低速状态；阵风后能否及时恢复；一瓶释放后多久再次稳定；空载时会不会出现较满载更快的振荡。把实际 RELEASE 等待原因统计出来，才知道需要改飞控、视觉还是动作设计。

例如，持续侧风要求飞机以 11° 横滚才能保持位置，即使姿态控制非常好，也可能一直无法通过 8° 门限。此时问题不是“P 不够大”，而是任务门限与飞行环境不匹配。处理应是重新评估环境、任务策略及安全条件，不是无条件放宽门限。

本文不假定你们已经把非任务区速度改成 12 m/s，也不假定 O4 侦察路线已经验证。原 v11 默认仍为较低转场速度和六点 RGB 拍照。关于 12 m/s 的制动与时间计算见第 55 章。

**需要补齐的实机信息**：CUAV 型号及硬件版本、ArduCopter 完整版本/构建标识、机架与桨直径、空机和两瓶载荷质量、ESC 型号与协议、电池、GNSS/RTK 型号、遥控协议、数传型号、供电图、当前全参数和一段原始 BIN。没有这些，不能负责任地给出一套“直接导入即可飞”的完整参数。

## 4. 学习、台架、试飞、比赛必须分开

把测试分成五级：

| 等级 | 内容 | 放行条件 |
|---|---|---|
| L0 离线 | 参数文件、日志、数学和合成数据练习 | 不连接飞控、不发送控制命令 |
| L1 无桨台架 | 电源、传感器、通信、RC、舵机、故障链 | 所有螺旋桨拆下，载荷有支撑 |
| L2 隔离仿真 | SITL、异常注入、模式与参数保存试验 | 与真机串口、网络路由完全隔离 |
| L3 开阔场试飞 | 基础悬停、滤波、AutoTune/QuickTune、制动 | 合格飞手、观察员、清场、可中止方案 |
| L4 任务验收 | 满载/单瓶/空载，完整任务和异常分支 | 前三级已通过，逐级提高复杂度 |

**任何电机测试和电调配置都先拆桨。** 不允许用手抓住带桨飞机证明控制方向正确；不把绑在桌上的强约束机体当自由飞行模型整定；不在室内、桶上方 1.3 m 或狭窄比赛走廊第一次做自动调参。

每次带桨试飞前，飞手必须能回答：如何立即结束当前调参？如何切到已经验证的可控模式？定位不可用时哪个模式仍可用？什么情况下必须落地？谁负责宣布中止？安全开关是否会切断所需的动力，而不是仅改变界面状态？

调参阶段的人工开关操作是**赛前试验**，不要把它放进要求自主执行的正式比赛过程。比赛现场要求以当轮正式规则和裁判说明为准；本教程不是参赛资格或法规解释。[S05](#s05)[P2](#p2)

## 5. 版本管理：4.6 的参数不能按 4.7 的单位照抄

【资料核对】官方仓库的 `Copter-4.7.1` 发布条目标为非预发布、稳定版，发布日期为 2026-09-04。本文查阅日为 2026-09-05。**这不代表你们正在使用该版本，也不构成比赛前升级建议。**[G01](#g01)

ArduCopter 4.7 对大量参数进行了改名和 SI 单位转换。地面站旧截图、旧教程、旧参数文件与新固件混用，是非常实际的风险。[G06](#g06)[G07](#g07)

| 项目 | 4.5/4.6 常见旧写法 | 4.7 对应写法 | 阅读规则 |
|---|---|---|---|
| 水平航点速度 | `WPNAV_SPEED`，cm/s | `WP_SPD`，m/s | 1200 cm/s 与 12 m/s 相等 |
| 水平航点加速度 | `WPNAV_ACCEL`，cm/s² | `WP_ACC`，m/s² | 数值通常除以 100 |
| 航点半径 | `WPNAV_RADIUS`，cm | `WP_RADIUS_M`，m | 不只是换名字 |
| 最大倾角 | `ANGLE_MAX`，centideg | `ATC_ANGLE_MAX`，deg | 3000 与 30 表达同一角度 |
| 横滚最大角加速度 | `ATC_ACCEL_R_MAX`，centideg/s² | `ATC_ACC_R_MAX`，deg/s² | 不是线加速度 m/s² |
| 俯仰/偏航最大角加速度 | `ATC_ACCEL_P_MAX/Y_MAX` | `ATC_ACC_P_MAX/Y_MAX` | 同样检查角度单位 |
| 最后下降速度 | `LAND_SPEED`，cm/s | `LAND_SPD_MS`，m/s | 50 与 0.50 表达同一速度 |
| Loiter 速度 | `LOIT_SPEED`，cm/s | `LOIT_SPEED_MS`，m/s | 模式不同，不等于 GUIDED |
| 起飞前检查 | `ARMING_CHECK`：旧版 bit 0 表示全部 | `ARMING_SKIPCHK`：0 表示不跳过 | **位掩码语义相反，不能复制数值** |

这个表是查找入口，不是自动转换器。尤其位置控制器 `PSC_*` 的迁移涉及名称、单位和某些增益缩放，不能把所有值机械地除以 100。固件内置迁移代码、对应版本参数说明和实际读回结果必须一起核对。

一些网页已换成新参数名，但段落仍残留旧单位或旧数字。本文遇到矛盾时明确区分“网页描述”和“固定版本源码”，不把网页中的旧量纲当成真机配置依据。附录 B 给出更完整的版本阅读方法。

建议锁定三件东西：**飞控固件版本/构建、地面站版本、脚本提交版本**。准备好上一版已验收 `.apj`、参数备份、脚本和日志；实际降级也应先确认参数兼容，不能只刷新固件而把新参数结构原样留下。

## 6. Mission Planner：从连接到真正读懂界面

Mission Planner 是配置和诊断工具，不是“配置向导点完就自动安全”的认证程序。本文以 Windows 上常见操作为例，菜单可能随版本显示为 SETUP/CONFIG/DATA 或 Initial Setup/Config-Tuning/Flight Data。

首次操作顺序：

1. 全部拆桨；确认供电、线束无短路；不启动 MAVROS 和其他串口客户端。
2. 使用可靠 USB 数据线连接，选择实际出现的 COM 端口。充电线不能代替数据线。
3. 等待参数完整下载，查看消息区中真实固件版本、板型和报错。
4. 保存一次全参数和消息记录，作为接手这架飞机时的原始状态。
5. 在 HUD 中缓慢改变机体姿态，确认显示方向和实际动作一致，再进入后续校准。

常用页面分工：

| 页面 | 用途 | 典型陷阱 |
|---|---|---|
| Mandatory Hardware | 机架、加速度计、罗盘、遥控 | 校准顺序混乱或未重启 |
| Optional Hardware | 电源、数传、RTK、传感器 | 按别的硬件套型号 |
| Full Parameter List/Tree | 参数原名、帮助、读写 | 写入后未读回；旧元数据 |
| DATA / Messages | STATUSTEXT、模式、解锁状态 | 只截最后一行错误 |
| DataFlash Logs | 机载 BIN 下载与分析 | 把地面 tlog 当全采样日志 |
| Radio / Aux Function | 开关与输入核对 | 同一开关绑定不同危险功能 |

写入参数后要确认：是否成功回显、是否注明需重启、重启后是否保留、功能是否通过无桨验证。**界面字段改了，不等于飞控已经使用了新值。**[S06](#s06)[S07](#s07)

<a id="c07"></a>
## 7. 参数备份、差异审阅与回滚

建议每次变更保存四份信息：变更前全参数、变更后全参数、变更理由和对应日志。目录可用：

```text
vehicle_V6X_01/
  manifest.md
  firmware/
  params/
    20260905_01_before.param
    20260905_02_after_notch.param
    20260905_03_after_quicktune.param
  scripts/
  flights/
    F001_empty_hover/
    F002_two_payload_hold/
  changes.csv
```

参数文件通常是名称和值；还可能有注释、逗号或制表符，以及 QGroundControl 的 system/component/type 列。**不要用简单“按空格取第二列”的脚本处理所有格式。**本教程的离线解析器见第 62 章，遇到重复名称、非有限值和不认识的格式会拒绝猜测。

变更记录至少说明：哪个假设、只改了哪一类参数、为何预期有效、可能副作用、如何判失败、怎样回滚。把“感觉稳了”改成“相同电池状态、相同载荷、相似风况下，角速度跟踪与动作后收敛时间均改善，电机温度及饱和未恶化”。

别把全参数从另一架飞机导入作为初始设置。其中包含板级引脚、校准、传感器设备 ID、机架输出、RC、失效保护、导航源等。即使同型号 CUAV，也不代表传感器校准、线束和执行器一致。

此外，飞控 `.param`、ROS `.yaml`、GNSS 接收机内部配置、数传配置、Lua 的持久参数是不同的配置域。备份一个文件不能覆盖整架飞机。[S07](#s07)

<a id="c08"></a>
## 8. CUAV 接口：以实物型号和对应硬件定义为准

CUAV 不同型号的接口和固件目标可能不同。**本文用 V6X 的公开映射作教学例子，不能把它当你们尚未确认型号的实机或全部 CUAV 飞控的接线表。**同名系列还可能有硬件修订、载板与固件目标区别。

官方 V6X 页面给出的串口映射示例是：`SERIAL0` 对应 USB；`SERIAL1` 对应 TELEM1；`SERIAL2` 对应 TELEM2；`SERIAL3/4` 对应 GPS1/2；还有 TELEM3、USER、DEBUG 等接口。具体 MCU UART 名不是配置时最先需要记住的东西，**实物接口→SERIAL编号→协议→对端**才是接线表的核心。[S08](#s08)

| 实物接口 | 计划接入 | 必须核对 |
|---|---|---|
| POWER | 匹配的电源模块 | 电压范围、模拟/数字测量、供电能力 |
| TELEM | 数传或伴随计算机 | TX/RX/GND、逻辑电平、流控、SERIAL 映射 |
| GPS | GNSS 及可能共线的罗盘 | UART 与 I²C 针脚不能混接 |
| CAN | DroneCAN GNSS/电源/ESC | H/L、终端、电源、节点协议 |
| RCIN / 支持串口 | RC 接收机 | SBUS/CRSF 等协议及电平要求 |
| MAIN / AUX / M / A | 电机和投放舵机 | 输出功能、协议分组、独立供电 |

**不要仅凭插头能插进去或导线颜色相同判断兼容。**对照针脚图，用万用表确认地线、电源，确认接口看的方向是正面还是线束端。TTL UART 不等于 RS-232，5 V 供电端也不代表信号脚耐受 5 V。

V6X 的厂商页面与 ArduPilot 页面在部分输出分组、DShot 支持表述上存在差异。因此本文不把“A1～A8 全都支持某协议”写成普遍保证。以你们**实际板型的固定固件 hwdef、厂商修订说明及无桨测试**共同确定。模拟舵机与 DShot 电机不能在受相同定时器约束的输出组中随意混用。[S08](#s08)[S09](#s09)[G10](#g10)

<a id="c09"></a>
## 9. 电源：很多“飞控报错”其实从这里开始

典型系统至少有动力电源、飞控逻辑电源、舵机电源、伴随计算机电源和图传电源。它们可以共用电池，但不应把各自大电流直接压到飞控外设口上。

```text
电池 ── 主电源/电流测量 ── ESC与电机
  ├── 合适的飞控电源模块 ── CUAV
  ├── 合适的稳压电源 ── NUC / D435i
  ├── 合适的稳压电源 ── O4
  └── 合适的 BEC ── 投放舵机电源轨
```

这是功能图，不是可直接照焊的针脚图。电压、持续电流、峰值电流、保险和是否需要隔离必须按器件规格设计。信号通常需要共同参考地，但高电流回路应避免穿过敏感信号地线。两个 BEC 的正极也不能未经设计并联。

重点做组合负载检查：O4 发射、NUC 推理、RTCM 注入和两路舵机动作同时发生时，飞控有无重启、GNSS 是否重连、USB 是否掉线、电源温度是否异常。无桨台架不足以复现电机满负载压降，应把后续安全试飞日志纳入验证。

模拟电压校准的基本关系是：

\[
M_{new}=M_{old}\frac{V_{reference}}{V_{display}}
\]

它仅适用于对应的线性比例参数和可靠的参考测量。先确认 `BATT_MONITOR` 类型及引脚/总线正确，再调整比例；数字电源模块不要盲目套模拟模块的 `BATT_VOLT_PIN`。

电流校准需要区分零偏与比例。充电器回充量只能作为带有损耗、静置用电等影响的辅助核对，不能把一次差值精确等同于飞行电流传感器误差。电池低压和容量失效保护必须基于真实电池、负载压降与返航余量，而不是只按“6S”给全队同一个电压值。[S10](#s10)[S11](#s11)[S12](#s12)

<a id="c10"></a>
## 10. 机架、重心、安装与振动先于 PID

检查桨是否损伤、安装方向是否正确、电机轴是否弯曲、螺丝是否过长顶到绕组、飞控减振是否被硬线束跨接、GNSS 支架是否摆动、瓶子和挂架是否相对机体运动。松散的机构会形成控制器没有建模的弹性自由度。

两瓶水的质量与位置会改变重心、转动惯量和悬停推力。一瓶掉落后还可能左右不对称。应测量：空载、A1 挂载、A2 挂载、双瓶四种静态配置。**“单瓶状态”不一定只有一种。**

将电池滑动位置用于配平可以改善稳态，但每次改动后要更新重量与重心记录；不能边改机械边调 PID，最后说不清哪个改动起作用。

小角度与刚体力臂例子：飞控参考点下方 0.32 m 的机构，8° 倾斜会使这一段垂向力臂产生约 `0.32×sin(8°)=0.0445 m` 的水平投影。姿态稳定对投放精度重要，但实际投放中心还取决于机构标定和水瓶脱离方式。[P1](#p1)

不要把飞控物理中心、EKF 报告位置参考点、GNSS 天线相位中心、整机重心、相机光心和瓶子质心当成同一点。后续第 33、54 章分别讲导航和任务外参。

<a id="c11"></a>
## 11. 机架类型、输出映射与无桨电机测试

先在实际固件中选择正确的机架类别和布局，例如四旋翼 X；再对照该布局的官方电机图确定电机编号、转向和安装位置。Mission Planner 的电机测试 A/B/C/D 顺序不应凭直觉等同于固件电机 1/2/3/4。[S13](#s13)

无桨测试要逐个记录：点击哪个测试输出、实际哪个电机转、旋向如何、开始可靠旋转的输出范围。只在所有输出均一致后，才允许安装正确对应的桨。

`SERVOx_FUNCTION` 决定输出用途。输出口本身的编号和电机功能编号是两回事。重映射后尤其要检查投放舵机 9/10 没有占用电机功能，也没有被其他功能持续覆盖。

错误机架/方向的典型特征是离地瞬间快速翻滚，而不是缓慢收敛差。此时继续增加增益会使错误反馈更强。正确处理是停止试飞，回到输出与传感器方向检查。

**阶段实践 A：**画一张俯视机架图，标出前方、四个电机功能编号、实际输出口、旋向、桨型、两瓶位置和飞控朝向。另一个队员仅根据图复核，无需操作者口头提示即可核对全部接口。

<a id="c12"></a>
## 12. PWM、DShot、ESC 遥测与输出组冲突

PWM 通过脉宽表达命令；DShot 通过数字帧表达命令。它们的配置、标定方法和诊断方式不同。**DShot 不做传统油门高低端点校准**；是否使用何种 DShot 速率，应依据 ESC、飞控输出支持和布线可靠性，而不是越高越好。[S14](#s14)[S15](#s15)

不要把 `MOT_SPIN_ARM`、`MOT_SPIN_MIN`、油门曲线与遥控油门校准混为一谈。前者与电机可重复启动、低输出控制余量有关；RC 校准是输入映射。具体参数值需要通过对应动力系统验证。

ESC 遥测可能经独立串口、双向 DShot 或 DroneCAN 返回。配置“数字电调”不代表飞控已经收到 RPM。还要检查电机极数/电气转速到机械转速换算、每路更新是否连续、个别 ESC 是否失联。[S16](#s16)

同一输出定时器组常有共同的速率/协议限制。你们 SERVO9/10 需要模拟舵机脉宽时，不可因启用另一输出的 DShot 而间接把这两路也改成数字电机信号。

验证顺序是：无桨通信和单电机输出→转速与温度反馈合理→基本飞行日志→必要的 RPM 跟踪陷波。不要一次同时更新 ESC 固件、换协议、改极数、开双向遥测和运行 AutoTune。

<a id="c13"></a>
## 13. 加速度计与飞控安装朝向

先配置实际安装方向，再进行对应校准。六面加速度计校准估计传感器偏置和比例等误差；“Calibrate Level”用于把机体水平基准与实际安装微小偏差关联，两者不是互相替代。[S17](#s17)

校准应在不解锁、不晃动的条件下进行。每个姿态放稳后再确认，不需要快速甩动。柔软支架、持续震动的桌面和未固定的线束都会降低质量。

完成后用独立物理直觉检查 HUD：机头上抬、右侧下压、水平放置时，显示是否一致。不能只看“校准成功”弹窗。

机体基准面不是随手找的桌面，也不一定是相机底面。用团队约定的结构基准，并记录电池和载荷是否影响机体支撑姿态。改变飞控安装角、软支架或载板后需要重新评估。

**错误做法：**因为飞机向左漂，就把 AHRS 安装角改到看起来不漂。这样可能同时污染任务视觉外参和姿态估计。应先分清传感器水平基准错误、罗盘误差、风和位置环行为。

<a id="c14"></a>
## 14. 陀螺仪、温度与 IMU 振动

上电时保持机体静止，让初始陀螺仪零偏估计有正常条件。把刚从低温环境拿出的飞机立即起飞，与热稳定后的控制和高度表现可能不同，应记录环境和飞控温度。[S18](#s18)

振动有两个不同观察方向：加速度计 VIBE/Clip 反映测量环境；高频角速度日志与频谱反映控制器输入的噪声及结构/电机频率。VIBE 较小不自动证明所有角速度噪声都小。

官方将约 30 m/s² 以下描述为通常可接受的振动水平，超过 60 m/s² 常伴位置或高度问题。这里仅作为排查信号，不能变成“29.9 必然安全、30.1 必然失败”的比赛验收线。还应看裁剪计数是否在飞行阶段持续增长、多 IMU 是否一致、噪声是否与油门相关。[S19](#s19)

先消除松动、不平衡、线束跨接减振、共振支架，再处理滤波。不使用高 D 去补机械松动，也不把所有滤波频率降得很低来掩盖裁剪。

温度校准属于进阶工作，只有在对应板型和流程明确、能控制实验环境时开展；不要把用户自行烘烤硬件当作普通新手必做步骤。

<a id="c15"></a>
## 15. 罗盘、航向与磁干扰

罗盘校准应在远离大块铁磁物体、汽车、钢筋密集地面及高电流设备的环境中进行。先完成姿态方向与加速度计校准，再校准磁力计。外置罗盘的设备 ID、优先级、安装方向与使用状态都应记录。[S20](#s20)[S21](#s21)

对 CUADC，航向错误还会旋转整条 field 航线。若前方距离为 L，航向误差为 δ，横向偏差近似 `L sinδ`。L=60 m、δ=2° 时约 2.09 m。**定位达厘米级并不能抵消两度航向误差。**

静态校准合格以后，还要检查电流相关磁干扰：电池线绕过罗盘、O4/数传供电、舵机动作和动力负载是否使估计航向变化。保持线束布局一致，避免赛前临时捆扎改变电流环路。

不是罗盘越多越好；也不是把内部罗盘全禁用就必定正确。应根据安装环境、健康状态和日志确定选择，并保留设备 ID。自动识别安装方向也可能在磁场被污染时失败。

“马桶圈”式位置绕圈可由航向错误引起，但还可能与定位和外环有关。不要只靠现象给出唯一诊断，更不要直接增大 Loiter P。先比较实际机头方向、飞控航向、GNSS 轨迹和期望加速度方向。

<a id="c16"></a>
## 16. 遥控校准、飞行模式和辅助开关

校准 RC 输入时让飞控记录每个通道的最小、最大和中位，确认 RCMAP 对应正确、摇杆反向与死区合理。除油门外，摇杆回中应落在死区内；发射机的 trim、混控和曲线不能让调参脚本持续误判飞手在操作。[S22](#s22)

建议把操作权限分开，不用一个开关叠加多种危险功能：

| 功能 | 设计要求 |
|---|---|
| 模式开关 | 至少有已验证的人工可控模式和任务模式 |
| 紧急停止 | 明确、独立、可盲操作，理解恢复后电机可能恢复输出 |
| AutoTune / QuickTune | 赛前临时独立分配；两种整定不得共用运行 |
| 舵机手动测试 | 仅无桨台架，正式比赛前解除不需要的绑定 |
| 任务启动确认 | 与真正解锁、比赛计时顺序协调，不暗含调参启动 |

例如 Lua QuickTune 使用 `RC7_OPTION=300` 时，含义是“RC7 驱动 Scripting1 辅助功能”；`QUIK_RC_FUNC=300` 读取这个功能，不是读取第 300 个 RC 通道。

开关的机械低/中/高位置，与接收机上报 PWM 的大小可能因反向而颠倒。必须逐位置看输入和功能状态，并贴标签。启动时低位、失联时接收机行为也要验证。不能靠经验认定“往上就是保存”。[S23](#s23)

<a id="c17"></a>
## 17. 安全按钮、解锁检查与紧急停止

安全按钮、`armed` 状态和电机是否实际产生推力构成不同层级。某些输出可能被安全掩码豁免；舵机供电也可能不受电机停转控制。比赛所要求的安全开关应通过真实功能验证，而不是只看到地面站出现 SAFE 字样。[S05](#s05)[S24](#s24)

保留正常起飞前检查。旧版本的 `ARMING_CHECK` 和新版本的 `ARMING_SKIPCHK` 要按第 5 章理解，**不要照网上常见“设0解决无法解锁”教程处理所有错误**。检查被关闭后，故障并没有消失，只是不再被拦住。

遇到 PreArm 报错时，记录完整首个错误、当前模式、电源来源、是否有桨、位置环境、固件版本以及前一次改动。解决原因后再重试，不以反复解锁代替定位。

紧急停止开关要在无桨台架上验证：触发是否确实停止所需输出、解除是否会在仍 armed 时恢复动力、飞控和舵机供电是否仍在、飞手能否确定当前状态。真实飞行中动力切断会导致坠落，只作为与风险相称的紧急手段；普通调参中止优先使用调参专用停止/回退及已验证飞行模式。

**阶段实践 B：**让两名队员分别执行“解释开关—台架操作—读回状态”，互相检查。任何人说不清某开关解除后的行为，该配置不得放行。

<a id="c18"></a>
## 18. 双投放舵机：从飞控输出到水瓶脱离

【源码事实】v11 对 SERVO9/10 使用 1200 μs 挂载、1500 μs 释放、保持约 0.7 s 后回位。这是当前软件契约，**不是所有舵机和投放机构的通用行程**。[P1](#p1)

设置专用输出时，要确认实际针脚、`SERVOx_FUNCTION`、脉宽范围、协议组及安全状态允许方式。`MAV_CMD_DO_SET_SERVO` 需要输出功能可被该命令控制；已用于电机或其他主动功能的输出不能按普通舵机测试处理。[S25](#s25)[S26](#s26)

台架顺序：先空机构、支撑住载荷、确认机械限位，再逐步检查挂载—释放—回位。观察舵机是否持续堵转、BEC 电压是否下降、一次释放是否会碰到另一瓶、信号失联/飞控重启后机构位置是否安全。

三个“成功”必须分开：

- 命令发送成功：伴随计算机发出了请求。
- 飞控 ACK：飞控接受了请求或返回执行结果。
- 物理释放成功：水瓶实际离开且落点合格，需要独立观测或传感器证据。

因此不要用“ACK 次数=成功投放次数”来判断机构可靠性。v11 已把超时/迟到 ACK 视为物理状态不确定；现场还应验证断电、回位失败和载荷卡住时的处理。首次调参中不释放水瓶，首次投放试验也不同时运行调参。[P1](#p1)

<a id="c19"></a>
## 19. 日志、SD 卡与“必须保留什么”

机载 DataFlash BIN 记录飞控实际状态，是调参主要证据；地面 `.tlog` 记录收到的 MAVLink 消息，会受链路、消息频率和丢包影响；ROS bag 则记录伴随计算机看到的状态与目标。三者应按同一架次归档，不能互相替代。[S27](#s27)[S28](#s28)

每次试飞至少保留：BIN、前后参数、地面消息、载荷配置、电池编号、风况估计、操作时间线。任务联调还要记录 setpoint、odom、视觉消息时间戳、状态机状态和释放命令/ACK。

`LOG_DISARMED` 有利于记录上电和地面初始化，但会增加存储和写入。高频原始 IMU、批采样和完整 PID 日志也有带宽与 CPU/SD 负担。根据本次试验问题选择，确认没有持续日志丢弃和主循环过载。

日志下载在地面进行。不要在快速任务或 QuickTune 时同时通过低速数传下载大日志。传输挤占带宽可能同时影响 RTCM 和状态消息，制造出“GPS 和视觉同时不稳定”的假象。

**阶段实践 C：**不飞行，先学会导出一次全参数、保存消息窗口并打开已有示例日志。练习找出固件版本、模式变化、armed 状态和日志起止时间。

<a id="c20"></a>
## 20. 第一架次应做什么，而不应做什么

第一架次只验证基本飞行，不执行任务，不开视觉闭环，不做 12 m/s，不投瓶，不自动调参。准备工作必须由能够稳定操纵该机的飞手确认。

起飞前台架已经验证所有传感器与电机方向；实际离地后检查姿态能否稳定、油门与高度是否可控、是否有明显振荡或异响。出现快速振荡、方向异常、严重掉高、异常偏航等就按预先方案中止，不在空中试一串未知增益。

一个合理的递进是：基础姿态可控→AltHold 可控→定位健康时 Loiter→日志检查机械和滤波→基础整定→AutoTune 或 QuickTune→外环和输入整形→载荷包络→任务控制。

官方流程强调先让飞机基本可飞、评估机体、处理滤波，再进入自动整定。新手不应独立完成带桨的第一架次；教程可以教清原理和步骤，但不能替代现场飞手的即时判断。[S02](#s02)[S29](#s29)[S30](#s30)


<a id="c21"></a>
## 21. 串口、USB、I²C、CAN：从电气层开始排查

先问“是什么电气接口”，再问“跑什么协议”。USB、TTL UART、CAN 是不同物理接口；MAVLink、UBX、RTCM、DroneCAN 是不同的数据格式或协议。

| 接口 | 典型连接 | 最常见错误 |
|---|---|---|
| TTL UART | TELEM、部分 GNSS | TX/RX 未交叉、无公共地、误用 RS-232 电平 |
| USB | PC/NUC 与飞控 | 充电线、端口被占用、线材/接头震动 |
| I²C | 部分外置罗盘 | 拉线过长、地址冲突、供电不符、把 SDA/SCL 当 UART |
| CAN | DroneCAN GNSS、ESC、电源 | H/L 接反、缺终端、总线速率/驱动不对 |

UART 最小连接一般是飞控 TX→设备 RX、飞控 RX←设备 TX、共同信号参考地。设备供电另按硬件说明处理，不能默认把电源正极也连在一起。需要 RTS/CTS 时，线束和两端配置都必须支持，不能只打开参数。

`SERIALn_PROTOCOL` 指协议；`SERIALn_BAUD` 指对应 UART 速率。常见 ArduPilot 枚举中 57 表示 57600、115 表示 115200，**不是 57 baud 或 115 baud**。本文出现的枚举是阅读示例，实际仍应在对应版本参数帮助中确认。[S31](#s31)

CAN 需先启用实际物理总线对应驱动，再选择 DroneCAN 协议。节点还可能有自己的固件、节点 ID 和参数。通常 CAN 线两端需要终端电阻；断电后约 60 Ω 可作为两只 120 Ω 并联的线索，但设备内部电路会影响测量解释，不能带电测电阻，也不能只凭此数值证明总线正常。[S32](#s32)[S33](#s33)

**练习：**画出从“PC 软件”到“RTK 接收机”的每一层：应用→协议→端口→线束→电平→电源。遇到无数据时逐层证明，不从“修改 EKF”开始。

<a id="c22"></a>
## 22. 推荐的系统分工：遥控、数传、伴随计算机、O4 分开

下面是功能拓扑，不指定尚未知的硬件端口：

```text
地面遥控器 ── 独立RC链路 ── 接收机 ── CUAV
地面Mission Planner ── 数传链路 ── 机载数传 ── CUAV
NUC上的MAVROS ── USB/可靠本地串口 ── CUAV
D435i ── USB ── NUC视觉节点
O4相机/机载端 ── O4数字视频链路 ── 地面显示/判读
RTK基站 ── PC注入/独立修正链路 ── 机载GNSS
```

每条链路承担不同职责。O4 画面清楚不证明 MAVLink 没丢包；地面站连接正常不证明遥控器有效；GNSS 固定解也不证明 D435i 时间对齐。

对于你们的 30 Hz odom，机载本地链路应优先可靠、短路径、高可测性；不要为了省一根线，让高频飞行状态必须先绕地面无线链路再返回机载计算机。

RTCM 可以通过 MAVLink 数传共享发送，也可以用独立修正链路。共享节省硬件但增加拥塞耦合；独立链路减少耦合却增加电源、频率、端口和配置管理。选择依据应是端到端测试，而不是“模块宣传多少公里”。

任何总线都应指定一个明确的数据发送者和参数控制者。多台地面站、MAVROS、自动配置脚本同时修改参数或请求流频率，会出现“自己没改，它却又变了”的问题。[S34](#s34)[S35](#s35)

<a id="c23"></a>
## 23. SiK 数传：从配对到实际链路验收

这一章**只适用于运行 SiK 固件的数传**，不应把相同设置套到所有 CUAV 无线模块。先确认硬件型号、频段、固件和所在地点允许的发射要求。[S36](#s36)

常见配置流程如下，全部在无桨地面完成：

1. 给地面数传接 USB，给机载数传可靠供电并接好天线；不要让飞控同时被其他串口程序占用。
2. 在地面站的 SiK Radio 配置页面选择地面模块 COM 口并读取 Local Settings。
3. 确认无线连接后读取 Remote Settings；读不到远端时先检查供电、天线、匹配参数与距离。
4. 按该型号要求设置匹配的网络 ID、空中速率、频率范围、纠错/链路选项，再写入并读回。
5. 分别确认地面和机载模块的串口速率与各自接入设备一致；飞控对应 SERIAL 端口选择 MAVLink 协议。
6. 退出数传配置页，再建立正常 MAVLink 连接。观察消息、参数读取、丢包和 RSSI 类指标。

**串口波特率与空中速率不是一回事。**高串口速率不能突破无线链路吞吐；两侧 UART 是否必须同值由设备工作方式决定，但每一侧都必须与其直连设备匹配。

网络 ID 区分链路，不等于加密，也不能消除同频干扰。两队比赛时仍要做频谱/信道协调，遵守场地与当地要求，不在现场靠非法增加功率解决问题。

验收应依次测试：近距离静态→人员和设备工作时→预期最差方向与距离→同时加入 RTCM 与实际消息流。小天线贴电池、金属机架遮挡、极化不一致、两端放太近造成接收饱和，都可能使“桌面测试”与飞行结果完全不同。[S36](#s36)[S37](#s37)

<a id="c24"></a>
## 24. CUAV 专用数传、网络数传和供电问题

CUAV 品牌下不同数传可能使用透明串口、厂商私有无线协议、网络接口或不同的配置工具。**本文未收到具体型号，所以不虚构统一的“CUAV 数传默认密码/波特率/无线 ID”。**拿到型号后应先读对应手册，并填写附录中的端口记录表。

所有型号共通的配置核对项是：输入电压与峰值电流、逻辑接口、串口模式、UART 波特率、是否透明传输、半双工/全双工行为、空中吞吐、网络端口、天线频段、加密配对、固件版本和参数保存方式。

对带网络接口的设备，再核对 IP、子网、UDP/TCP、监听/发送端、系统防火墙和单向/双向 NAT 行为。能 ping 通仅证明部分网络路径，不证明 MAVLink 目标系统、端口和消息路由正确。

高功率数传不应直接假定由飞控 TELEM 电源脚供电。不同 CUAV 板的外设口电流能力不同；必要时使用匹配的独立稳压电源，信号接地方案按厂商电路要求。飞控偶发重启、GNSS 丢失或 USB 重连，要同时检查这一路供电。[S38](#s38)

现场排障时先缩小到一对数传、一个地面站、一块飞控。最小系统稳定后再加入 NUC、RTK 和 O4。对未识别型号的软件指令、恢复出厂快捷键、固件刷写方法，不凭其他品牌经验操作。

<a id="c25"></a>
## 25. 带宽预算、30 Hz 导航流与消息率争用

8N1 UART 的理想有效字节率近似 `baud/10`。115200 baud 对应约 11520 byte/s，这还没有扣除协议开销、重传、队列和无线调度。

先按实测或估计的**完整链路帧**做预算。例如若某类完整帧按 60 byte 估计，30 Hz 就需要 1800 byte/s；同时三类便是 5400 byte/s，再加心跳、状态、参数、RTCM 和 ACK。这里的 60 byte 只是教学假设，不是所有 MAVLink 消息的长度。

MAVLink 消息率有多种来源：默认流组、`SRx_*`、地面站 REQUEST_DATA_STREAM、逐消息 `MAV_CMD_SET_MESSAGE_INTERVAL` 等。`SERIAL2` 不应未经核对直接对应 `SR2_*`；SERIAL 编号描述物理逻辑串口，SR 实例和 MAVLink 通道映射还需看固件实际连接。[S31](#s31)[S39](#s39)

`MAV_CMD_SET_MESSAGE_INTERVAL` 使用消息 ID 和以微秒表示的间隔；命令被 ACK 接受仍不意味着已经稳定达到目标频率。必须观察消息到达间隔、长尾和丢帧，特别是在解锁、任务启动、RTCM 注入和日志下载期间。

【源码事实】你们的 `/cuadc/nav30_ready` 由外部节点提供，v11 还要求视觉时刻能被间隔不大于约 50 ms 的 odom 样本夹住。**平均 30 Hz 不排除偶尔 100 ms 的空洞。**航点控制 20 Hz、odom 30 Hz、GNSS 更新率、IMU 采样率、飞控主循环频率是不同层级。[P1](#p1)

建议记录：平均频率、中位间隔、95/99 分位间隔、最大间隔、超过 50 ms 的数量及出现时的其他活动。先查链路和队列，再怀疑 GNSS；不要把 GPS 输出频率改成 30 Hz 当作 NAV30 的修复。

<a id="c26"></a>
## 26. MAVLink 系统 ID、路由、连接独占与信息安全

同一 MAVLink 网络中的设备通过 system/component 等标识区分。两队飞机、两台地面站或多个路由器混在同一广播网络，可能出现错误绑定、重复消息和状态串线。

一根串口原则上交给一个主程序管理，再通过明确路由转发给需要的程序。Mission Planner、MAVROS、串口监视器直接抢同一个设备，可能造成无法打开或数据被拆分读取。重启程序只能暂时改变抢占顺序，不能解决架构问题。[S35](#s35)

如果使用 mavlink-router 或 MAVProxy，需要画出每个输入/输出端点，防止一个包经多条路径重新回到原点。重复心跳和消息会污染带宽统计，甚至让“某个进程已经死了”仍被其他发送者的心跳掩盖。

MAVLink2 消息签名可用于认证/抗重放层面的防护，但不等同于加密视频或隐藏数据。无线网络 ID 更不是访问控制。重要的是只允许预期终端连接，妥善保存密钥，不把 NTRIP 密码和飞控网络凭据提交到公开仓库。[S40](#s40)

**只读检查示例（Linux，不启动飞行）：**

```bash
ls -l /dev/serial/by-id/
# 将下面设备替换为已核对的实际节点
lsof /dev/ttyACM0
# 仅查看，不根据示例盲目结束系统服务
ros2 topic hz /mavros/local_position/odom
ros2 topic echo /mavros/state --once
```

这些命令只能证明局部状态。权限错误应按系统和设备所有者配置解决，不把全局 `chmod 777` 当永久办法。

<a id="c27"></a>
## 27. GNSS 基础：3D Fix、Float、Fixed 分别说明什么

卫星接收机的位置解有不同质量状态。常见 MAVLink GPS 状态中，3D Fix、RTK Float、RTK Fixed 是不同枚举；“Fixed”通常指载波相位整周模糊度固定解，不是说飞机被固定在空间中。[S41](#s41)

| 指标 | 说明什么 | 不能单独证明什么 |
|---|---|---|
| 卫星数量 | 当前参与/可见程度的一部分 | 几何一定好、没有多路径 |
| HDOP | 几何相关的精度稀释指标 | 真实误差等于这个数值的米数 |
| hAcc/vAcc | 接收机给出的精度估计 | 独立地面真值误差 |
| RTK Fixed | 模糊度解状态 | EKF 健康、罗盘正确、落点合格 |
| 修正龄期 | 最近有效修正的新鲜程度 | 基站坐标正确、星座消息齐全 |
| EKF 状态 | 融合估计是否满足当前逻辑 | 每个传感器单独完美 |

GNSS 天线需要开阔天空视野、适当的地板/安装方式和牢固支架。钢结构、墙边、树下和 O4/数传等射频设备的供电或布局干扰，会影响结果。不能把天线移到一个更好看的位置后忘记更新外参。

室内通常不具备正常 GNSS/RTK 使用条件。室内出现 EKF 或 GPS PreArm 拒绝并不需要关闭安全检查“解决”；室内测试应使用隔离仿真或已明确设计的非 GNSS 导航方案。

<a id="c28"></a>
## 28. RTK 的两种“基站”：固定地面基站与机载移动基线

**固定基线 RTK 定位**：地面基站观察卫星，发送修正信息；机载 rover 利用修正求更高精度位置。**GPS for Yaw / moving baseline**：两个机载天线的相对基线用于估计航向。二者可以同时存在，但不是同一功能。[S42](#s42)[S43](#s43)

```text
固定基站定位：
已知或测定坐标的地面天线 → RTCM → 机载 rover → 位置

移动基线航向：
机载天线A ⇄ 基线解算/修正 ⇄ 机载天线B → 航向
```

只有一个 RTK rover，不会因此自动获得静止航向。飞机静止时的航向仍可能来自罗盘、双天线系统或其他被明确配置的源。“有两个 GNSS 插口”也不代表两块任意 GPS 就能组成航向系统。

固定基站的坐标误差可能表现为整套解的共同偏移。相对同一局部基准的短时定位仍可能很好，但地图绝对位置和跨场次复现会受影响。移动基站、换修正源或在飞行中重新确定基站坐标，可能导致不连续，不应在任务中随意进行。

本文不预设你们使用的是哪一款 CUAV C-RTK 或 ZED-F9P 配置。C-RTK 系列不同型号的定位/航向能力、接口与固件配置方法应分别确认。[S44](#s44)[S45](#s45)

<a id="c29"></a>
## 29. 固定 RTK 基站：从安装到坐标确定

基站先有稳定的安装，再谈精度。选择开阔环境、稳定三脚架、明确天线参考点，不在金属车顶随意挪动后继续使用旧坐标。记录天线型号、序列号、安装点、天线高的定义和坐标来源。

两种常见基站模式：

| 模式 | 用途 | 风险 |
|---|---|---|
| Survey-in | 在未知点自主统计得到基站位置 | 通过时间/估计精度门槛不等于获得测量级绝对坐标 |
| Fixed position | 输入已有可靠坐标，重复使用固定站点 | 坐标基准、经纬度顺序、天线位置或高度填错 |

不要把“设置 60 s、某个 accuracy threshold”写成所有地点的通用精度保证。时间只反映收集过程；现场多路径和坐标基准不会因等一分钟自动消失。

基站页面显示的**survey complete**、串口有数据、RTCM 已发送、机载 rover 收到、rover 已 Fixed 是五个不同节点。排查时逐个确认。独立基站 USB 被别的软件占用，也会导致地面站注入失败。

保存固定点之前确认设备确实在该位置；重新使用保存坐标时，天线必须回到同一参考位置，且高度定义一致。地面海拔、椭球高、天线杆长度不是一个量，不能直接互换。[S42](#s42)[S46](#s46)

**阶段实践 D：**制作基站卡片，写清站点坐标来源、天线高参考面、日期、修正格式、允许使用的固定安装位置。没有这些元数据的“基地坐标.txt”不作为可信站点记录。

<a id="c30"></a>
## 30. 机载 RTK rover：UART 与 DroneCAN 两条配置路线

### UART 路线

确认 GNSS 供电与协议后接入实际 GPS/UART 端口；在飞控对应 SERIAL 端口选择 GPS 协议，设置接收机驱动类型和自动配置策略。部分版本用 `GPS_TYPE`，较新配置常见 `GPS1_TYPE`；应以实际参数列表为准。

若接收机由飞控自动配置，不要同时让外部工具反复改串口速率和输出消息；若采用手动接收机配置，应保存其内部配置，并清楚飞控是否会在重启时覆盖。**飞控参数保存不等于 GNSS 接收机内部配置已保存。**

### DroneCAN 路线

确认是 DroneCAN 设备而不是“插头长得像 CAN 的其他协议”。启用物理 CAN 驱动与 DroneCAN，读取节点、设备 ID、固件和 GNSS 实例，确认每次重启分配关系一致。使用双 GNSS 时更要避免两个实例互换而参数外参仍按旧编号解释。[S32](#s32)[S33](#s33)

两条路线都必须检查：位置更新、卫星/解类型、精度估计、速度、RTCM 到达情况、重启后的配置、接收机供电和天线连接。不能只看罗盘正常就判断同一线束上的 GNSS 一定正常。

旧 C-RTK 文档可能基于早期 ArduCopter 版本，功能枚举和菜单不能直接套给 4.7。先确认型号和实际驱动选项，再使用该型号手册的接线与操作步骤。[S44](#s44)

<a id="c31"></a>
## 31. 通过 Mission Planner 给飞机注入 RTK 修正

标准共享链路形态为：基站→PC→Mission Planner→MAVLink 数传→飞控→机载 GNSS。[S42](#s42)[S47](#s47)

可按以下端到端检查表操作：

1. 地面站先与正确的飞机建立 MAVLink 连接，确认 system ID 和型号。
2. 在 RTK/GPS Inject 页面选择实际基站设备的 COM 口及串口速率；这不是飞机的 COM 口。
3. 完成基站 Survey-in 或载入可信固定坐标。
4. 观察输入数据计数和修正发送计数，不把页面停在“已连接”就结束。
5. 在飞机端观察 GNSS 状态是否从单点/Float 进入 Fixed，记录建立时间和修正中断后的行为。
6. 加入实际任务所需状态流，再重复测试，检查 RTCM 与遥测是否争抢带宽。

RTCM 消息和星座应与基站、rover 能力匹配。F9P 常见的是站点信息、各星座 MSM 观测信息及必要的偏差信息；具体消息清单和输出率按接收机固件手册，不在不知道接收机型号时硬塞一份配置。

若用独立无线电直接向 rover 送 RTCM，必须明确接到哪个接收机输入、那个输入是否允许 RTCM、是否存在第二个注入源。**不要让不同基站的修正流无规则混合。**

关闭地面站、PC 休眠、无线断开都会影响这条修正链路。飞行中若依赖它，应事先测试失去修正后 Fixed→Float/单点及 EKF、状态机的整体行为，而不是期待图传还在就一定安全。

<a id="c32"></a>
## 32. NTRIP：网络修正不是“插上网就 Fixed”

NTRIP 通常涉及 caster 地址、端口、mountpoint、账号、密码和客户端。部分服务需要客户端发送 GGA 以选择或生成附近虚拟参考站。是否需要 GGA、坐标如何提供、使用哪个 mountpoint，以服务说明为准。[S48](#s48)

```text
修正服务/参考站网络
        ↓ Internet
NTRIP客户端（例如地面PC）
        ↓ RTCM
Mission Planner/MAVLink数传
        ↓
飞控 → rover
```

逐层确认：域名可解析→TCP/协议连接成功→认证成功→正确 mountpoint→持续收到非空修正→注入正确飞机→接收机实际使用。HTTP/认证成功页面不是 RTCM；网络连通也不保证延迟小和服务覆盖合适。

账号密码存放在本机受控配置，文档截图打码，仓库中用占位符。不要把含密码的连接字符串写进公开启动脚本、终端截图和日志。

比赛使用互联网还要考虑手机热点省电、流量耗尽、场地蜂窝拥塞、PC 休眠、网卡切换和服务可用性。能否采用自有固定基站或备份修正路径，应结合赛场要求和已经验证的切换机制；**不在空中临时切换未知基准的修正源。**

**实践：**仅在地面记录 10～20 分钟修正龄期、解类型和数据中断，不移动基站、不启动飞行。统计中断持续时间，比看一次 Fixed 截图更有价值。

<a id="c33"></a>
## 33. 双天线航向、杆臂与 FRD/FLU 的符号

双天线航向的配置需要：兼容的接收机、正确的 base/rover 角色、已知安装基线方向和长度、所需内部修正链路、正确的 EKF yaw 源。**把两个 RTK 模块都设成普通 GPS，不会自动得到航向。**[S43](#s43)[S45](#s45)

基线不能晃动。两天线若装在柔软支架上，振动会改变真实基线；传感器报告的“精度”也不能替代结构稳定性。

杆臂是传感器相对约定机体参考点的位置。ArduPilot 传感器位置参数通常使用机体前、右、下的 FRD；你们 v11 投放口外参使用前、左、上的 FLU。转换关系为：

\[
[x,y,z]_{FRD}=[x,-y,-z]_{FLU}
\]

例如投放口 `[+0.026,-0.065,-0.32]` FLU 对应 `[+0.026,+0.065,+0.32]` FRD。**这是坐标转换示例，不是要把投放口位置填写到 GPS 杆臂参数。**GPS 参数必须测量天线位置，并核对厂商与固件所约定的机体参考点。[S70](#s70)

双天线航向可以在没有外部固定站修正的情况下工作，是否有绝对位置 Fixed 与是否有有效 moving-baseline yaw 要分别观察。起飞前缓慢改变机头方向，检查航向方向、零偏、180° 反向、遮挡后一致性，再做受控试飞。

你们 field 航线通过起飞时航向定义前方。即使用双天线 yaw，也仍需确认起飞摆放是否平行场地中心线。高质量航向源不能修正“摆歪了起飞”的场地标定错误。[P1](#p1)

<a id="c34"></a>
## 34. EKF 源、低空高度与参考点

EKF 不是简单把所有传感器取平均。它需要明确的位置、速度、高度和航向来源，并根据模型、噪声与创新检验融合信息。`EK3_SRC1_POSXY/VELXY/POSZ/VELZ/YAW` 等参数表示选择的观测源，实际枚举请在运行版本帮助中读取。[S49](#s49)

对室外 GNSS 飞机，常见设计是水平位置/速度来自 GNSS，姿态由 IMU 等融合，垂向结合气压计与速度观测，航向来自罗盘或已验证的 GNSS yaw。**这只是结构说明，不是一份必须导入的 EKF 源组合。**

低空投放最容易混淆三个高度：

- GNSS 给出的绝对高度及其参考基准。
- EKF 本地 z 与任务锁定 home_z 之差。
- 投放口到当前地面或桶口的实际距离。

v11 的 1.3 m 是基于本地 odom 的机体参考点相对高度，不是飞控自动保证出瓶口距桶口 1.3 m。地面高差、baro 压力误差、天线/IMU/机构杆臂都会影响解释。[P1](#p1)

RTK Fixed 不意味着 GNSS 高度一定适合直接取代全部低空高度观测。加装向下测距仪也需要明确量程、朝向、盲区、表面适应性、延迟与融合/地形用途。不能仅因“更准”就把 `EK3_SRC1_POSZ` 改成另一个源。[S50](#s50)

出现 EKF 源报错，优先核对所选择的传感器是否存在并被实际送入飞控。ROS 里存在一个 `/vision/pose` 话题，不等于飞控收到并融合了外部导航；D435i 做桶识别也不是自动在提供 VIO。

<a id="c35"></a>
## 35. RTK 的验收：固定解率只是第一项

完整验收应包含静态、动态、遮挡和重启四组测试。下面的时间与阈值是**试验设计示例**，不是官方统一准入标准。

| 试验 | 记录内容 | 能回答的问题 |
|---|---|---|
| 固定地面点静置 | 解类型、修正龄期、hAcc/vAcc、本地位置散布 | 短时重复性与链路连续性 |
| 同一点断电重启 | 新 home、base坐标、局部原点、绝对坐标 | 跨次基准是否一致 |
| 开阔地慢速移动 | 解类型变化、速度、延迟、位置跳变 | 动态连续性 |
| 地面中断修正 | Float/单点出现时间、恢复时间 | 修正链路故障后行为 |
| 开启 O4/数传/舵机 | 与静态基线相比的变化 | 电源、射频或带宽耦合 |

没有独立真值时，应写“散布/重复性”，不要写“绝对误差”。有测量基准时，也要明确它的坐标参考系和误差。

检查“总是 Float”按顺序拆分：基站是否稳定并有效→RTCM 是否持续→正确发给本机→rover 接收协议是否正确→共同星座与信号是否足够→是否有遮挡/多路径→频宽和修正龄期→接收机配置及固件兼容。

检查“Fixed 但漂”则分开看：GNSS 原始定位是否跳、EKF 是否切换/重置、磁航向是否错、飞控是否在跟踪移动 setpoint、基站是否移动、机体和机构参考点是否一致。不要把所有现象都归因于卫星数量。

配套 `rtk_metrics.py` 只分析导出的示例 CSV，报告 Fixed 可用时间、数据空洞和龄期条件，不把它当作自动放飞程序。


<a id="c36"></a>
## 36. 控制环：先分清自己正在调哪个环

一个有用的简化模型是：

```text
任务轨迹/位置目标
       ↓
位置误差 → 速度目标
       ↓
速度误差 → 加速度/推力方向目标
       ↓
姿态误差 → 角速度目标
       ↓
角速度误差 → 力矩指令
       ↓
混控/控制分配 → 各电机输出
```

真实实现有前馈、限幅、输入整形和耦合处理，不是这张图的简单串接，但它能帮助定位问题。[G06](#g06)[S51](#s51)

最内层角速度环大致可写成：

\[
u=K_P e+K_I\int e\,dt+K_D\frac{de}{dt}+u_{FF}
\]

其中 `e=期望角速度−实际角速度`。P 产生即时纠偏，I 处理持续偏置，D 对变化敏感、可提供阻尼但也放大噪声，FF 根据目标运动提前提供作用。ArduPilot 的具体 D 处理、滤波与限幅应以实际实现为准，不能把这个教学公式当固件逐行定义。

| 参数族 | 主要含义 | 一般不负责 |
|---|---|---|
| `ATC_RAT_RLL/PIT/YAW_*` | 角速度跟踪 | 相机外参、地图坐标 |
| `ATC_ANG_RLL/PIT/YAW_P` | 姿态误差到角速度目标 | GNSS 绝对精度 |
| `ATC_INPUT_TC` 等 | 指令响应形状 | 消除供电或振动故障 |
| `PSC_*` | 位置/速度/垂向控制 | 修复错误电机顺序 |
| `LOIT_*`、`WP_*`/`WPNAV_*` | 模式/轨迹速度和动态限制 | 把飞机无限加速 |
| `INS_*`、各 PID 滤波 | 信号处理 | 创造不存在的传感器信息 |

内环不稳定时不要先猛调外环。外环要求的姿态越激烈，可能越快暴露内环和动力问题。

积分饱和也要理解：当电机已经到上限，继续积累误差不会带来更多推力，反而可能延长恢复。看到大 I 时要问是增益不合理、长期重心偏置，还是输出能力不足。

<a id="c37"></a>
## 37. 怎样用日志判断“调参不对”

按时间顺序找：目标什么时候变化→实际什么时候跟随→输出是否饱和→传感器是否失真→模式是否改变。先定位起因，再看最后的结果。[S27](#s27)[S30](#s30)

| 观察 | 可能含义 | 还需排除 |
|---|---|---|
| 角速度目标平稳，实际高频噪声大 | IMU噪声、结构振动、控制振荡 | 记录率/绘图混叠 |
| 目标阶跃后超调、来回摆 | 环路阻尼/延迟/增益问题 | 上层目标反复改变 |
| 目标明显领先，输出已贴上限 | 动力或控制分配饱和 | 电池压降、桨问题 |
| 姿态跟踪很好，位置绕圈 | 定位/航向/外环问题 | field坐标方向错误 |
| 释放瞬间高度变化 | 质量突变、机构动作、压力扰动 | 视觉或本地高度坐标跳变 |

常用日志族包括 ATT、RATE、PIDR/PIDP/PIDY、RCOU、CTUN、BAT、VIBE、GPS/GPA、XKF 和各类事件。不同固件的字段名、单位和实例可能变化，先查看 BIN 内 FMT/UNIT/乘数定义或日志工具的字段说明，不把网络截图中的曲线列名照搬。[S28](#s28)

对同一片段同时画期望与实际。只画实际角度曲线，无法区分“飞机不听话”和“上层命令本来就在动”。姿态角小也不一定意味着位置精度高；高频小幅抖动仍可能让图像模糊和电机发热。

比较调参前后时，不仅比较 P 值大小。记录 RMS/分位误差、最大超调、整定时间、持续输出不平衡、热量、电池和载荷。一次良好飞行不能证明整个包络。

<a id="c38"></a>
## 38. 推力曲线、悬停油门与载荷变化

飞控输出不是天然与推力线性。电机、桨、电调、电池电压和空气条件共同决定推力响应。推力曲线、悬停推力估计及电池补偿会影响垂向控制和控制余量。[S52](#s52)

`MOT_THST_HOVER` 或对应悬停学习功能反映某种条件下的悬停输出估计，不是“只要设成 0.5 就最稳定”。自动学习有条件和时间常数，不能期待投掉一瓶后瞬间完成整套重新辨识。

理想定高、倾角为 θ 时，忽略阻力等因素所需总推力为：

\[
T=mg/\cos\theta
\]

因此高倾角转场需要额外推力余量。空载能快速飞，不代表双瓶满载也能保持高度；低电压时情况可能更差。电机输出饱和后，调整 PID 不能增加硬件最大推力。

**配置包络建议**：记录双瓶、仅 A1、仅 A2、空载的悬停输出与控制分配；记录新电池与允许最低工作电量附近的差异。单瓶左右两种情况都测，因为相同质量可能有不同重心偏置。

官方调参流程强调在较灵敏的配置下建立基础整定，通常涉及较小起飞重量和充分电量；这与任务满载验收不冲突。本文的工程建议是：先按适用官方流程建立稳定基线，再验证所有任务载荷，**不是不加区分地“永远满载 AutoTune”或“空载调完直接比赛”**。[S02](#s02)

<a id="c39"></a>
## 39. 滤波：为什么应在自动整定前完成

D 项对高频噪声敏感。滤波不当时，QuickTune 可能把噪声引起的控制输出变化当作振荡边界，AutoTune 也可能基于污染的响应得到不合适增益。先改机械，再建立合理滤波，是整个流程的前置条件。[S53](#s53)[S54](#s54)

常见概念：

| 名称 | 作用 | 代价或限制 |
|---|---|---|
| 低通滤波 | 抑制高频部分 | 越低的截止频率通常引入越多相位影响 |
| 固定陷波 | 抑制某段固定频率 | 电机转速变动时可能跟不上 |
| 谐波陷波 | 同时针对基频及选定倍频 | 过多陷波增加复杂性与计算量 |
| RPM 跟踪陷波 | 根据有效转速移动中心频率 | 依赖可靠、正确换算的 RPM |
| FFT 跟踪 | 从传感器频谱识别频率 | 需要合适配置和资源，不能修复传感器裁剪 |

`INS_HNTCH_*` 等描述惯性传感器陷波；`ATC_RAT_*_FLTT/FLTE/FLTD` 描述各控制器输入/误差/导数滤波。名字都带 FILTER 并不代表同一层。[S53](#s53)[S55](#s55)

推荐的验证过程是：安全的基本悬停获取日志→看噪声与转速的对应→选择适用的陷波来源→读取前后频谱并看控制响应→确认 CPU/日志无明显问题→才运行自动整定。

不要把网页给的一组 `FREQ/BW/ATT/HMNCS` 不经动力参数核对导入。也不要只看滤后曲线漂亮就继续提高带宽；滤波延迟、控制输出和电机温度一起看。

脚本里的 `QUIK_AUTO_FILTER=1` 只按 INS_GYRO_FILTER 设置部分 PID 滤波，不会替你完成整个动态陷波设计。它可能改动刚刚手动验证过的 FLTT/FLTD，因此要在执行前决定由谁管理滤波，并审阅调参后的差异。[G02](#g02)

<a id="c40"></a>
## 40. 手动初调：目标是得到可安全辨识的基线

手动初调不等于随机旋转滑块。它要在机体、方向、供电、定位及初始滤波可信的前提下，通过小范围、单因素的改动让飞机基本可飞，给自动整定提供起点。[S51](#s51)

对新手，优先使用与实际桨径、动力和机架匹配的官方初始设置流程，在有经验飞手监督下验证。不要从完全无法悬停的飞机直接启动 QuickTune，因为脚本仍要实际飞行并逐渐改变增益。

每次只提出一个可检验假设。例如“释放摇杆后明显低频回摆，角速度跟踪有超调，输出未饱和，可能需要调整阻尼”；然后依据对应版本调参指导作小范围变更，试飞、记录、比较。不能从“感觉慢”直接得出 P 应加倍。

保守的停止条件应预先定义：振荡增强、异响、电机快速升温、异常偏航、输出贴限、定位质量下降、进入边界或电量不足。出现这些先终止实验，再分析，不在同一次飞行中继续盲试。

本文不提供任意机型的 P/I/D 数值，因为缺少实机动力、惯量、滤波、采样条件与日志。你们真正应该形成的是“何时该改哪一类参数，以及怎样证明改动有效”的能力。

## 41. 三种自动调参：必须先选对名字

| 项目 | ArduCopter 内置 AutoTune | 官方 Lua VTOL-quicktune | 内置 C++ QuickTune（含该功能的构建） |
|---|---|---|---|
| 主要入口 | AUTOTUNE 模式/辅助功能 | SD 卡 Lua applet | 固件内的 AP_Quicktune |
| 参数前缀 | `AUTOTUNE_` | `QUIK_` | `QWIK_` |
| 常见控制 | AutoTune 辅助功能，编号17 | Scripting 功能，默认300 | QuickTune 辅助功能，编号181 |
| 行为特点 | 主动施加测试动作，识别响应 | 悬停中逐渐寻找角速度环增益边界 | 与 Lua 相关但实现和保护有差异 |
| 保存主流程 | 接受后保持相应状态，落地上锁（disarm）时保存 | **落地前 HIGH 保存，确认 saved** | 按对应版本 QWIK 流程 |
| 核心限制 | 基本可飞，需试验空域 | 基本可飞、滤波健康、脚本 API 匹配 | 固件必须实际编入并支持当前模式 |

辅助功能的枚举以实际固件为准，不因表格出现了数字就省略开关测试。[S23](#s23)[G02](#g02)[G03](#g03)[G05](#g05)

**三者不能同时运行。**Lua 脚本和 AutoTune 同时写同一组 ATC 参数，会让各自的“原始值”“测试值”“保存值”失去清晰意义。

不要把 Plane 固定翼 AutoTune、传统直升机 AutoTune 和多旋翼 AutoTune 的参数表混用。它们可能有相同名称，但识别过程、轴定义和适用条件不同。

对你们的 CUADC，可以把 QuickTune 理解为一种建立/改善角速度环基础整定的工具，AutoTune 用于进一步的动态识别；**并非每架飞机都必须连续跑两种，最终选择以适用流程和验收结果为准**。不是“两种都点过”才叫调好了。

<a id="c42"></a>
## 42. 内置 AutoTune：准备、参数与版本差异

AutoTune 会真实地改变控制行为并主动施加测试运动。所需空间由机型、风、导航质量和试验响应决定，不能沿用投放时 1.3 m 的低空高度。选择开阔、安全、风较平稳的试验条件，并安排飞手随时中止。[G03](#g03)

运行前确认：基本 AltHold 可控，定位模式使用时 GNSS/航向健康；机械无明显摆动，松散云台和载荷问题已解决；滤波已验证；电池余量足够；原参数已导出；AutoTune 的开启/退出开关已无桨核对；ROS 自动任务、其他调参脚本未运行。

固定版本 `Copter-4.7.1` 的 `AC_AutoTune_Multi.cpp` 显示：

| 参数 | 该源码默认值 | 含义与注意 |
|---|---:|---|
| `AUTOTUNE_AXES` | 7 | bit0 Roll、bit1 Pitch、bit2 Yaw、bit3 YawD |
| `AUTOTUNE_AGGR` | 0.075 | 用于 D 项识别的回弹判据，不是航速 |
| `AUTOTUNE_MIN_D` | 0.0005 | D 的下限，不应为掩盖噪声盲调 |
| `AUTOTUNE_GMBK` | 0.25 | 对辨识结果作增益回退的比例，版本相关 |

**不要把网页或旧教程的 AGGR 默认 0.1 当成所有固件事实。**本文明确引用该固定版本的 0.075；实机读回优先，已保存参数也可能不同于编译默认值。[G03](#g03)

AXES 是位掩码：3 表示 Roll+Pitch，7 表示 Roll+Pitch+Yaw，15 还包括 YawD；YawD 并不是飞机多了第四个几何旋转轴。是否调 yaw D 要结合机架、噪声和实际版本能力，不能默认“选得越多越好”。

AGGR 较小不等于所有条件下必然更安全。它改变识别判据，噪声和响应也影响结果。先使用对应流程，再依据日志和版本说明调整，不为了“保守”把它设到范围外。

<a id="c43"></a>
## 43. 内置 AutoTune：完整的执行、试飞与保存流程

以下使用辅助开关方式描述，具体模式名称和保存细节必须与运行固件一致。该流程与固定版本源码头部的操作说明一致，官方页面也给出了对应流程。[G03](#g03)[S68](#s68)

**起飞前：**保存原参数；开关处于关闭 AutoTune 的位置；机体、失效保护、场地、电量和飞手准备全部完成。

**建立悬停：**使用已经验证的控制方式起飞，进入合适的 AltHold 或官方支持的定位辅助入口，在足够空间内稳定。不要让状态机同时发送任务位置目标。

**开始整定：**启用 AutoTune。飞机会进行一系列测试动作，地面站报告轴和阶段。飞手以安全为最高优先级，不追求一口气完成全部轴。

**重新定位：**源码说明在飞手操作重新定位及测试间隔使用原增益；摇杆释放后继续。该行为不能套到 Lua QuickTune，后者见第 47 章。

**结束并比较：**完成整定后，按对应模式/辅助开关方式切出再切回，测试新增益；必要时回到原增益比较。不要因为出现成功消息就立即认定适用于所有载荷。

**接受结果：**对本章普通辅助开关流程，保持 AutoTune 接受/测试状态，受控落地，并在该状态下 disarm，使结果永久保存。随后导出参数、重启读回，再与前值比较。

**拒绝结果：**落地上锁前退出 AutoTune、恢复原增益；确认没有保存新值。任何异常先以安全结束飞行为主，回到地面后用备份核对实际参数，不在空中为争取保存而冒险。

### 为什么“我调完了，重启后又变回去”

整定完成、试用新值、写入持久存储是三个事件。你可能整定完成后切到普通 LAND/RTL 或关闭辅助开关，再落地上锁，结果并没有按接受路径保存。不同版本还可能支持 `AUTOTUNE_TEST_GAINS` 等额外机制；没有核对该版本之前，不把它与本章普通流程混为一谈。

### 不要照搬给 Lua

内置 AutoTune 的接受路径与 Lua QuickTune **落地前切 HIGH、看到 saved** 的路径不同。把两套步骤混在一起，是丢失整定结果的常见原因。

<a id="c44"></a>
## 44. AutoTune 卡住、失败或效果不佳怎么办

不要把每次不能完成都解释为“需要更激进”。先按下列证据定位：

| 现象 | 检查证据 | 处理方向 |
|---|---|---|
| 一直等待，不开始动作 | RC 是否真正回中、模式、入口条件、消息 | 修复入口/操作条件 |
| 反复测试某轴 | 噪声、风、结构摆动、响应一致性 | 改善实验条件与基础滤波 |
| 达到限值或终止 | ATUN/ATDE、PID响应、输出余量 | 判断识别是否有效，不直接抬限值 |
| 位置漂得很远 | 使用模式、定位与航向、风 | 中止并恢复位置，不赌剩余几次测试 |
| 整定后电机发热 | 高频输出、D、滤波和电机状态 | 回退，分析噪声与输出 |
| 手动很灵敏但任务不稳定 | 上层目标抖动、外环、输入整形 | 不把手感当任务验收 |
| 重启后参数未保留 | 保存分支、实机读回、日志 | 按持久化流程重新核对 |

回退不一定是全部重做。若某次只改变一个轴或一组滤波，应通过参数差异明确恢复范围；若版本、校准或机架配置也被改动，则需要完整复核。不要随便把两次整定中“看起来大的 P、小的 D”拼起来。

AutoTune 产生的是候选整定，不是无人值守飞行的许可证。通过小幅阶跃/缓和姿态动作、定位悬停、任务转场、载荷变更和落地测试，才形成你们自己的验收证据。

## 46. Lua QuickTune 的 15 个参数逐项解释

下表依据上章固定 Lua 源码。它的配套 `.md` 还残留“增加 7 个参数”的旧描述；本表不据此删掉实际存在的参数。[G02](#g02)[G04](#g04)

| 参数 | 固定源码默认 | 教学解释 |
|---|---:|---|
| `QUIK_ENABLE` | 0 | 是否执行更新逻辑；**不是可靠的空中回退按钮** |
| `QUIK_AXES` | 7 | 位0横滚、位1俯仰、位2偏航；3只调横滚和俯仰 |
| `QUIK_DOUBLE_TIME` | 10 s | 增益按指数增长时翻倍所需时间；更长意味着更慢 |
| `QUIK_GAIN_MARGIN` | 60 % | 检测到振荡后计划减少的比例；60表示保留40%，还受其他约束 |
| `QUIK_OSC_SMAX` | 5 | 对控制器 slew-rate 指标的判断阈值，不是陀螺角速度门限 |
| `QUIK_YAW_P_MAX` | 0.5 | yaw P 的上界 |
| `QUIK_YAW_D_MAX` | 0.01 | yaw D 的上界 |
| `QUIK_RP_PI_RATIO` | 1.0 | 在相应条件成立时，roll/pitch 的 I=P/比例 |
| `QUIK_Y_PI_RATIO` | 10 | 在相应条件成立时，yaw 的 I=P/10 |
| `QUIK_AUTO_FILTER` | 1 | 是否按 INS_GYRO_FILTER 改部分 PID 滤波 |
| `QUIK_AUTO_SAVE` | 0 s | 0表示不自动保存；非零是在完成后等待再保存 |
| `QUIK_RC_FUNC` | 300 | 读取哪个辅助功能缓存，不是 RC 通道号 |
| `QUIK_MAX_REDUCE` | 20 % | 限制相对初始基线的最大增益降低量 |
| `QUIK_OPTIONS` | 0 | 位0启用两段开关行为 |
| `QUIK_ANGLE_MAX` | 10° | 目标姿态与实际姿态的误差角中止阈值，**不是绝对倾角限制** |

### GAIN_MARGIN 和 MAX_REDUCE 为什么看起来矛盾

假设初始 P=0.10，逐渐增加到0.20时检测到振荡。60%的回退计划得到0.08；20%的最大降低限制也允许最低0.08，所以一致。

如果在0.12检测到振荡，60%回退得到0.048，但 MAX_REDUCE=20% 的初始基线下限仍是0.08，最终会受限。两个参数分别约束“相对当前振荡点退多少”和“相对起始增益最多退多少”，不能只看一个。

### AUTO_FILTER 并非自动设计全部滤波器

该源码把当前轴 FLTT、FLTD 设置为 INS_GYRO_FILTER 的一半；yaw FLTE 仅在其低于0或高于8的条件下被设置到8。它不会重做你们的动态陷波，也不保证改变后相位和噪声最优。

### I 项并不总会跟着 P 改

源码在相应 FF 大于0时不做这项耦合；PI ratio 小于1时也不按上述公式更新 I。不要仅根据默认比例推断所有飞机最后的 I 值。

### 不要随意关闭 ANGLE_MAX 保护

将它设为0会关闭该姿态误差检查。若频繁触发，应先检查机体、基础整定、噪声、风和增益增加速率。不能把保护阈值调大当作修复故障。[G02](#g02)

<a id="c47"></a>
## 47. Lua QuickTune 三段开关：停止、开始、保存

本章是最重要的操作卡。以一个已经确认空闲的 RC7 三段开关举例：地面设置 `RC7_OPTION=300`、`QUIK_RC_FUNC=300`；确认没有与模式、紧急停止、载荷或另一脚本冲突。示例通道不是强制使用 RC7。[G02](#g02)[G04](#g04)

| 开关逻辑值 | 普通三段开关 | 固定源码行为 |
|---|---|---|
| 0 | LOW | 停止整定；有未保存改动时恢复备份；复位中止锁存 |
| 1 | MID | 飞行条件允许时整定/继续 |
| 2 | HIGH | 保存已经改变的参数到持久存储 |

**LOW/MID/HIGH 按飞控实际收到的逻辑状态判断，不按开关外观方向。**

### 完整操作顺序

**地面准备：**备份参数；脚本加载正确；噪声/滤波和基本飞行已验证；只保留一种调参；开关在 LOW；建议初次使用 `QUIK_AUTO_SAVE=0`、普通三段开关，避免未评价就自动保存。

**进入试验悬停：**由飞手在合适空域、足够安全高度建立稳定 Loiter。官方说明以低风悬停为使用场景；试验高度应根据机型、扰动、场地和可恢复空间决定，不沿用任务低空高度。

**开始：**切 MID。观察 `Tuning: starting tune`、当前轴和当前 P/D、输出变化率信息。脚本默认顺序是 RLL_D→RLL_P→PIT_D→PIT_P→YAW_D→YAW_P。

**必要时操作飞行：**飞手始终优先保持安全。该源码检测 roll/pitch/yaw 输入后会延迟继续增益增加，直到输入停止约4秒；但它**没有因这件事自动恢复全部原增益**。不要把“暂停增长”理解成“已经回退”。

**接受：**完成后看到 `Tuning: DONE`，在仍有安全飞行余量的条件下评价响应。认可后切 HIGH，确认 `Tuning: saved`，**在落地之前保存**。然后按受控流程落地、上锁、导出参数、重启读回。

**拒绝或中止：**切 LOW，确认 `Tuning: reverted`（存在未保存更改时）。若脚本异常而不能确认回退，优先使用飞手已经掌握的安全操纵与降落方案；落地后用备份核对和恢复，不能在空中重启飞控作为回退方法。

### 保存的三个陷阱

第一，先 LOW 再 HIGH 会先丢弃未保存结果，不能用来模拟内置 AutoTune 的“低—高测试”。

第二，源码 HIGH 保存分支不要求所有轴 DONE，因此可能保存尚未完成的一组增益。新手应等完成且评价通过后再保存。

第三，已经 HIGH 保存后再 LOW，不能指望回到本次飞行最初的全参数，因为保存操作已经更新了内部备份。需要初始配置时，地面使用真正的外部备份回滚。

### 资料与源码的差异

部分网页描述把摇杆操作与恢复原参数联系起来；本文所固定 Lua 的实际分支只更新时间、暂停后续调参，不执行全参数恢复。控制输出的降增益过渡阶段还可能在暂停判断之前继续完成。因此**以专用 LOW 和回退消息作为操作依据**，而不是把动作相似的内置 AutoTune 习惯带过来。[G02](#g02)[S57](#s57)

## 48. Lua 算法推导：它为什么能在悬停中整定

这不是神经网络，也不在线计算完整机体动力学模型。它在基本可飞的悬停条件下逐步调整增益，用控制输出变化率指标识别接近振荡的区域，然后回退到较保守的水平。[G02](#g02)

### 48.1 每次增长多少

源码的名义更新率为40 Hz，增益翻倍时间为 τ：

\[
m=\exp\left(\frac{\ln2}{40\tau}\right),\quad g_{k+1}=m g_k
\]

τ=10 s 时，连续400次正常增长会使增益约翻倍。实际调参中暂停、状态延迟、异常调度和增益过渡会改变总耗时，所以不能说“六个参数一定60秒完成”。

源码末尾旧注释写10Hz，但函数返回 `1000/UPDATE_RATE_HZ`，常量为40，因此**名义调度是25ms**。Lua 调度不等于飞控内环硬实时频率；受到系统负载影响。[G02](#g02)

### 48.2 先 D 后 P

每个轴先处理 D，再处理 P。增加 P 时在无相应 FF、比例条件允许时关联调整 I。阶段间有约4s等待；增益回落还通过若干步渐变，而不是每次瞬间大跳。

如果降低了某些轴的 D，源码还有联动降低 P 的处理，以降低因此触发 P 振荡的风险。它不是只在参数表里找到一个数字乘倍率。

### 48.3 检测的到底是什么

脚本读取 `AC_AttitudeControl:get_rpy_srate()`，拿当前轴的 slew-rate 指标与 `QUIK_OSC_SMAX` 比较。这个指标来自控制器输出变化，不是直接拿 IMU 的角速度作比较，也不是在 Lua 中进行 FFT。

配套说明中将它写为 Hz 的表述不宜用作严格量纲教学；要按实际固件对 slew-rate 指标的定义理解，不能认为 OSC_SMAX=5 就等于“只检测5Hz振动”。这也解释了为什么传感器噪声和执行器动态都会影响判断。[G02](#g02)[G04](#g04)

### 48.4 它没有替你调什么

该 Lua 不完整辨识角度环 P、最大角加速度、位置环、垂向环、GNSS 噪声、相机时间延迟和风场。调出的增益也不代表真实投放口已经对准。它改善的是任务链路中的一部分。

### 48.5 离线数字练习

初始 D=0.004，振荡时 D=0.020，GAIN_MARGIN=60%，则计划结果为0.008。若原值0.015且 MAX_REDUCE=20%，下限为0.012，最终不会直接降到0.008。这只是算法约束演算，不构成真机 D 建议。

配套 `quicktune_math.py` 可重复这些计算，不包含飞控连接或参数写入。

## 49. 从源码读懂 Lua：变量、API、状态与保护

本文不重新编写可直接上机整定的替代脚本；官方脚本只提供固定版本链接。这里用函数索引帮助新人阅读官方源码。[G02](#g02)

| 函数/对象 | 做什么 | 阅读重点 |
|---|---|---|
| `Parameter()`、`bind_param()` | 绑定已有参数 | 名字不存在时会报错 |
| `param:add_table()` | 创建动态参数表 | KEY冲突与参数数量 |
| `bind_add_param()` | 添加 QUIK 参数并绑定 | 默认值≠实机当前持久值 |
| `get_all_params()` | 记录整定起点 | 在什么时候重新拍快照 |
| `restore_all_params()` | 将改过的参数恢复到快照 | 主要是RAM值，不代替外部备份 |
| `save_all_params()` | 使用 `set_and_save()` 写入 | 同时更新内部备份与标志 |
| `setup_filters()` | 改部分 PID 滤波 | AUTO_FILTER开关影响 |
| `have_pilot_input()` | 读取映射后摇杆/死区 | 不同于模式切换检测 |
| `adjust_gain()` | 改RAM值，可能连带改I | FF和ratio条件 |
| `limit_gain()` | 约束相对初始值的降低量 | 与GAIN_MARGIN分别作用 |
| `update()` | 调参主状态分支 | 判断顺序决定保护语义 |
| `protected_wrapper()` | 用pcall处理运行错误 | 捕获错误不等于恢复全部参数 |

Lua 的 `local` 表示局部变量；`function` 声明函数；表 `{}` 可作数组或字典；`obj:method(x)` 会把对象隐式作为第一个参数；`assert()` 不满足时产生错误；`pcall()` 捕获调用中的异常并返回成功标志和错误信息。

脚本末尾返回“下次要调用的函数”和“延迟毫秒数”，相当于协作式调度。不应写阻塞式长循环抢占资源，也不在高频循环不断写持久参数。

### 安全的第一段 Lua 实践：只读状态

以下完整文件可放在**无桨台架或隔离 SITL**中练习加载。它不修改参数、不发模式、不控制电机/舵机，也不执行 AutoTune。

```lua
-- bench_readonly_status.lua：只读教学，先在无桨台架/SITL验证
local function report()
    local label = arming:is_armed() and "ARMED" or "DISARMED"
    local p = param:get("ATC_RAT_RLL_P")
    local p_text = p and string.format("%.6f", p) or "unavailable"
    gcs:send_text(6, "LAB read-only: " .. label .. " RLL_P=" .. p_text)
end

local function update()
    local ok, err = pcall(report)
    if not ok then
        gcs:send_text(4, "LAB read-only error: " .. tostring(err))
    end
    return update, 2000
end

return update, 2000
```

完成后解释每一行，而不是马上加入 `set_and_save()`。所有被装进 scripts 目录的有效脚本都可能在启动时执行；“只是放在那里”不是可靠的停用方式。比赛部署应移走不需要的教学脚本并核对校验值。

## 50. Lua QuickTune 的异常与回退：比“怎么开始”更重要

### 50.1 `QUIK_ENABLE=0` 为什么不能当空中回退

固定源码一开始检查 ENABLE，小于1就直接返回。这个分支位于恢复原参数逻辑之前，所以可能停止继续整定，**但仍保留已经写进 RAM 的候选增益**。不能把关闭开关名称理解成恢复原参数。

### 50.2 切飞行模式为什么也不能保证停止

这份 Lua 没有像 C++ QuickTune 那样接受 `mode_supports_quicktune` 并据此恢复。官方建议 Loiter 使用，不代表脚本在每次模式切换后都会自动回退。使用专用 LOW 中止，并确认消息。

### 50.3 `pcall` 捕获错误并不自动撤销前面写入

外层捕获错误后发送 Internal Error，并延迟重试；它没有在异常处理分支中统一恢复参数。若错误发生在部分参数已改之后，物理飞机可能继续使用部分改动。此时飞手应按预先方案结束试验，落地后比较全参数。

### 50.4 缺 API、参数表冲突和内存问题

| 报错/现象 | 可能原因 | 安全处理 |
|---|---|---|
| 无 QUIK 参数 | 脚本未加载、目录/扩展名不对、功能未编入 | 无桨检查脚本内容与构建 |
| `could not find ...` | 脚本依赖的参数在该固件不存在 | 核对匹配版本，不删除断言硬跑 |
| `attempt to call ... nil` | Lua binding/API 不兼容 | 使用已验证组合或相同版本SITL验证 |
| `could not add param table` | 动态表KEY冲突或资源问题 | 移除重复/冲突脚本后地面重启 |
| `Must be flying to tune` | 不是armed+likely_flying，或开关太早 | 保持台架安全，不规避此条件 |
| 姿态误差 ABORTING | 实际与目标姿态误差超过保护 | 先终止，查动态与噪声 |
| 地面红色 loaded 消息 | 该源码用很高severity发送部分加载文本 | 读消息正文，不只看颜色 |
| 持续 Internal Error | 更新反复失败 | 不继续调参，不假定自动回退 |

### 50.5 校验值与比赛前清理

`SCR_LD_CHECKSUM` 和 `SCR_RUN_CHECKSUM` 可用于起飞前确认脚本集合。相关 `SCR_DEBUG_OPTS` 的生成校验功能按官方说明在地面使用，保留其他位并核对结果；不要遇到校验错误就清零绕过。[S56](#s56)

它们是起飞前检查的一部分，不是脚本运行时永不崩溃的保证。固定版本、参数快照和飞手中止能力仍然需要。

**最终原则：**先 LOW 并确认回退，再在地面停用/删除脚本；不以切 ENABLE、重启 Lua、重启飞控或空中上锁来替代受控中止。[G02](#g02)

## 51. 内置 C++ QuickTune：为什么不能照 Lua 参数表配置

较新的固件源码还包含 `AP_Quicktune` 的 C++ 实现。是否可用取决于实际编译配置和机型，必须在实机看到 `QWIK_*` 参数并核对对应文档，不能因为 GitHub 存在文件就认定所有 CUAV 固件都有。[G05](#g05)

固定 `Copter-4.7.1` 源码显示两者有实际差异：

| 项目 | 本文固定Lua | 固定版本C++实现 |
|---|---|---|
| 前缀 | QUIK | QWIK |
| RC控制 | `QUIK_RC_FUNC`，默认300 | 专门辅助功能，按固件核对181 |
| 最大降低名称 | `MAX_REDUCE` | `REDUCE_MAX` |
| OSC_SMAX默认 | 5 | 4 |
| yaw误差滤波上限常量 | 8 | 2 |
| 禁用ENABLE时 | 直接返回 | 有待恢复改动时调用中止 |
| 模式支持检查 | 无相同显式检查 | 有 `mode_supports_quicktune` 分支 |

因此，“关闭 ENABLE 会恢复”“切出支持模式会恢复”等保证不能从 C++ 实现推导回 Lua。本文第 47～50 章明确只描述固定 Lua 文件。

不要把两套同时装/启用用于比较。比较应在独立架次，保留共同基线和清晰参数快照，确认加载的是哪一套。机型不明、功能不在构建中时，不通过新增未知参数名称来假装启用。

## 52. 整定完成后的验收：空载、A1、A2、双瓶

完成自动整定后要做的是验证，不是再无休止地追逐更高增益。建议建立以下矩阵，并逐步推进，不在同一架次叠加多个首次试验。

| 配置 | 要验证的现象 | 特别关注 |
|---|---|---|
| 空载、充足电量 | 基础姿态、加减速、小扰动 | 最灵敏配置是否高频抖 |
| 双瓶、充足电量 | 悬停、转场、低速稳定 | 推力余量、热量、机械摆动 |
| 仅A1 | 同样动作 | 单侧重心、输出分配 |
| 仅A2 | 同样动作 | 与A1对称性是否成立 |
| 双瓶→单瓶→空载 | 有计划的载荷转换 | 高度扰动、姿态恢复、机构干涉 |
| 允许最低电量附近 | 已验证动作的低风险版本 | 压降、控制余量、返航余量 |

输入整形让飞机更柔和，不等于必须降低所有姿态 P。应在稳定内环基础上调整任务目标的速度/加速度/jerk 和适用模式的输入时间常数，减少目标本身的突变。

不要在每次投瓶后动态切换一套未经验证的 PID。固定的一组稳健参数覆盖整个任务包络，往往比复杂、没有验证的在线参数调度更可控。

验收记录应能回答：哪组参数、哪份滤波、哪一台飞机、哪个载荷、哪种环境、什么动作、用什么指标判断、下一步允许做什么。仅有 `Tuning: saved` 截图不能完成这些证明。

## 53. 高度、Loiter 与位置外环：AutoTune 之后还有工作

内置姿态 AutoTune 或 Lua QuickTune 不会自动把低空高度、Loiter 刹车和 GUIDED 位置响应全部整定好。这些要在稳定姿态基础上分别验证。[S03](#s03)[S04](#s04)[S49](#s49)

### 垂向控制

先检查高度估计是否可信，再看控制器。气压计受气流、机体外壳和日照温度影响，GNSS 高度也有不同误差；高度曲线跳动并不一定是飞机真的上下跳。对照视频、测距仪或独立标尺测量，以及垂向速度、加速度和推力。

下列问题有不同处理方向：

- 实际高度稳，但日志高度跳：先查观测与估计。
- 高度目标稳，实际缓慢漂：查高度源、偏差和外环。
- 投瓶瞬间上冲后缓慢恢复：查重量突变、悬停推力、垂向限幅与控制余量。
- 高速段掉高且电机接近饱和：查推力/倾角/电池，不先增加垂向 P。

### Loiter

Loiter 对飞手输入、制动、速度限制有自己的参数。`LOIT_*` 不是所有自主模式通用的速度开关。在 Loiter 调得舒服，不代表外部 GUIDED 连续位置目标也会同样响应。

### 外环调试方法

先用很小、平滑的目标变化观察位置与速度响应，确认无边界风险。比较期望位置、实际位置、期望速度和实际速度；若姿态已经准确跟踪，但位置仍超调，才进一步分析外环和目标动态限制。

4.7 的 `PSC_NE_*`、`PSC_D_*` 与旧版 `PSC_POSXY/VELXY/ACCZ...` 不能只通过名称相似猜增益等价。参照固件迁移及实际单位，不把本章当作全参数转换指导。

## 54. GUIDED、MAVROS 与你们的 v11：飞控必须满足哪些条件

【源码事实】v11 订阅 `/mavros/state`、`/mavros/local_position/odom`、罗盘航向及视觉消息，通过 `/mavros/setpoint_position/local` 发送位置目标，通过 CommandTOL 起降，通过 CommandLong 操作舵机。它不直接计算电机输出。[P1](#p1)

接入顺序应为：飞控独立手动/定位飞行验收→只读 MAVROS 状态→核对位置和姿态坐标→隔离仿真任务→低速小范围真实 GUIDED→任务区域搜索和投放。

必须特别区分以下几点：

**导航流新鲜不等于导航解可靠。** v11 的 odom 新鲜检查主要看数据是否及时到达，不直接等于 RTK Fixed 或 EKF 协方差门限。不能因为有30Hz消息就认为厘米级定位有效。

**收到时间不是硬件采样时间。** 当前 v11 对 odom 使用机载主机接收时刻入历史，视觉也按主机时钟对齐。共同时间域有价值，但无法消除上游传感器和串行传输延迟。[P1](#p1)

**速度字段还要看参考坐标系。** v11 从 odom.twist 计算水平模长和 z 速度。理解它们作为世界水平/垂直速度之前，必须核对实际 MAVROS 版本的消息 frame/child_frame 和发布实现；不能仅凭话题名推断。

**飞控角度与任务航向不是同一配置域。** 修改 AHRS、罗盘优先级或 GNSS yaw 后，任务锁定的初始航向、相机外参和 field 前方都要重新验收。

**任务参数不是飞控参数。** ROS 的 `search_speed_m_s`、`fine_align_alt_m` 与 ArduCopter 的导航速度、姿态和垂向限制共同决定最终行为。v11 的 rescue profile 还会覆盖部分 YAML 值，这不表示飞控 PID 被覆盖。

**脱离 GUIDED 不一定是飞手拨了开关。** 飞控自身 failsafe 也可能改变模式。状态机不得与飞控保护反复争抢模式；需要从日志区分主动接管与飞控保护事件。

## 55. 12 m/s 转场：必须先算加速度与刹车距离

这是对前面对话中高速方案的重要边界说明：**把速度参数写成12，不意味着30m转场就能按3秒完成。**这涉及动力、最大倾角、加速度、jerk、控制延迟和安全空间，而不是 AutoTune 是否跑完。

### 55.1 从12减到0需要多远

忽略jerk、风和控制延迟，恒定制动加速度 a：

\[
d_{stop}=\frac{v^2}{2a}
\]

再计入总反应/跟踪延迟 τ，近似：

\[
d_{required}\ge v\tau+\frac{v^2}{2a}+d_{margin}
\]

这不是最终飞行边界模型，但足以排除明显不可能的安排。

| v=12 m/s，假设a | 理想制动距离，不含额外裕度 | 加0.2s延迟后的距离 |
|---:|---:|---:|
| 2 m/s² | 36 m | 38.4 m |
| 3 m/s² | 24 m | 26.4 m |
| 4 m/s² | 18 m | 20.4 m |

表中加速度仅用于算例，**不是推荐给实机的参数值**。

若从12减到6 m/s，a=3 m/s²时，理想距离为 `(12²−6²)/(2×3)=18m`。所以“侦察区前留1.5m就能减完速”不能仅靠规划点位置保证。

### 55.2 30m的静止到静止，能达到12吗

对对称、加速度受限的理想轨迹，达到峰值v并再停下需要至少 `v²/a` 距离。a=3、v=12时为48m，30m不够；30m段的理想峰值仅 `sqrt(30×3)=9.49m/s`，总时间约 `2sqrt(30/3)=6.32s`，还未计jerk和跟踪误差。

### 55.3 你们原轨迹发生器隐含了什么

【源码推导】v11 `start_segment()` 使用20%加速、60%匀速、20%减速的时间分配，长段设定时长为 `T=L/(0.8v)`，不是根据独立最大加速度求解。[P1](#p1)

由此隐含的加速度约为：

\[
a_{implicit}=\frac{v}{0.2T}=\frac{4v^2}{L}
\]

L=30m、v=12m/s时约19.2m/s²。理想定高所需倾角约 `atan(19.2/9.81)=62.9°`，且需要很大的推力余量。**这不是宣称你们飞机会如此倾斜，而是证明该setpoint轨迹没有凭12m/s这个参数保证物理可实现。**

实际飞控会受到自身限幅、控制和动力约束，跟不上移动目标后仍要补追；`segment_complete()` 还要等实际飞机进到终点半径。因此只把轨迹时长相加得到的全流程时间不能当实飞上限。

### 55.4 建立速度包络的顺序

在足够大且安全的试验区，先低速证明刹车与跟踪，再逐级提高速度；每级记录满载/空载、最差电池状态、实际速度、制动距离、侧向漂移、最低高度、最大倾角和输出饱和。测试不通过就停在已验证级别。

8m宽任务区的软边界不是高速制动安全网。越界后才开始拉回的逻辑不保证飞行器投影从未越出物理边界。正常任务规划、真实飞控围栏、制动前瞻和失效处置需要分层设计。

**AutoTune 的价值是改善合理指令的跟踪，不是让物理制动距离消失。**

<a id="c56"></a>
## 56. 返航与降落：HOME、EKF原点和接地点

飞控 HOME、EKF 本地原点、ROS 节点锁定的 `home_` 和实际起降标志中心应分别记录。它们常常接近，但不能未经验证认定重合。[S58](#s58)[P1](#p1)

v11 使用自己锁定的 local home 返回，正常/故障返回也不是简单调用固件 RTL。飞控自身失效保护触发 RTL 时，则按它的 HOME、RTL 配置与导航能力工作。需要检查两种返回路径是否都处于允许区域。

降落相关速度、转段高度和地形使用在不同固件版本有改名，见第5章。不要让“返航快”变成“地面附近也高速下降”。还应检查桨下气流、地面反射、测距盲区、脚架触地和翻倒风险。[S59](#s59)

【源码事实】v11 的落地确认不依赖 ExtendedState，而用相对高度、速度与连续时间：实际有效门限约为相对高度绝对值≤0.12m、水平速度≤0.10m/s、垂向速度绝对值≤0.08m/s，持续至少2秒。[P1](#p1)

这是源代码针对场地问题采取的设计，**不是通用的触地传感器**。若起降点地面变化、高度估计偏移或低空悬停恰好满足阈值，纯odom判断仍需风险评估。不能为让程序结束，随意扩大阈值并在未确认触地时强制上锁。

最终停止动力应以实际落地、正确的飞控状态和任务逻辑共同确认。没有着陆反馈时优先保留飞手安全处置能力，而不是让程序通过“任务完成”文本掩盖不确定状态。

<a id="c57"></a>
## 57. 失效保护：不能只依赖 ROS 状态机

飞控、伴随计算机、RC和地面站可能独立失效。设计保护时要问“谁还能运行、谁还有控制权、它看到的故障是什么”。一个已经崩溃的ROS进程不能可靠地给自己发送返航命令。[S60](#s60)

| 故障 | 检测位置 | 需要验证的处置 |
|---|---|---|
| RC链路丢失 | 接收机/飞控 | 失联标志是否真实，模式/动作是否符合计划 |
| GCS心跳丢失 | 飞控 | 监听的是哪个系统，其他进程是否掩盖故障 |
| NUC任务节点死掉但MAVROS还在 | 独立任务监视机制 | 不能只看MAVROS心跳 |
| GNSS/航向严重不可信 | EKF/飞控 | 不再依赖坏位置做常规RTL |
| RTCM丢失但仍有GNSS | 接收机/质量监视 | 按定位质量和任务阶段降级，不把Float当必然失控 |
| 电池低/严重低 | 电池监视/飞控 | 足够提前量、返航和紧急落地策略 |
| 舵机状态不确定 | 任务节点/机构反馈 | 禁止重复盲投，保护剩余载荷 |
| 超围栏 | 飞控/任务规划 | 制动与返回空间，不能与外部指令争抢 |
| 脚本运行错误 | Lua/地面消息 | 停止调参、稳定着陆、地面核对参数 |

### 围栏不是搜索航线内缩的替代词

飞控围栏可包含以HOME为基准的范围及上传的多边形/圆形包含、排除区域，类型、使能和越界动作需要分别配置。上传任务航点不等于已经上传围栏；配置了围栏列表也要确认实际使能和采用的坐标/高度参考。[S69](#s69)

对CUADC狭长区域，不能用一个很大的HOME圆形围栏就声称已保护两侧边界。也不能把边界恰好贴在人员安全线，期待高速越界触发后瞬间停止。应结合制动距离、定位误差和返航路径设计缓冲区，先在隔离仿真中验证。v11的SEARCH软边界仅覆盖特定任务状态，不代替全任务飞控保护。[P1](#p1)

### RC、GCS与GUIDED超时不是一回事

Radio failsafe 看RC信息；GCS failsafe主要看相应MAVLink心跳；GUIDED目标超时依指令类型和版本处理。某些速度/加速度控制有停止更新后的超时行为，但**不能据此断言连续位置setpoint一停就自动RTL**。[S61](#s61)[S62](#s62)[S04](#s04)

`FS_OPTIONS` 可改变失联时是否继续 AUTO/GUIDED 或继续降落等行为。不要把网上一个位掩码复制给所有任务；逐项读所选位并写进失效矩阵。尤其不要误把与载荷释放有关的失效选项加进普通返航配置。

### 电池保护

低电量与严重低电量可设计不同动作，但需要真实电压/电流监视正确、判据与负载压降合理。仅根据静置电压推算可飞时间不够。高速满载增加电流，可能使电池保护更早出现；关掉保护不是提速办法。[S12](#s12)

### GPS不可用时

不具备可靠水平定位的飞机不能指望普通RTL解决所有问题。是否使用AltHold、Land或经过配置验证的其他机制，应由飞手能力、环境与固件支持共同决定。不要首次在真实比赛中验证死推算返航。

所有失效注入先在L1/L2执行。实际飞行中不要为“测试”突然关闭发射机、断飞控电源或拔线；必须采用单独评估的受控试验方案。

## 58. 常见报错（一）：连接、校准与不能解锁

以下是按机制组织的诊断表。报错文本会随固件有所变化，搜索时应保存原文；本表不是关闭检查的快捷清单。[S05](#s05)

| 报错或现象 | 第一轮检查 | 不要这样处理 |
|---|---|---|
| 找不到COM口 | 数据线、USB供电、驱动、系统设备列表 | 反复刷新未知固件 |
| COM端口被占用 | MP/MAVROS/终端/配置工具是否同时打开 | 多个程序同时重试抢端口 |
| Waiting for heartbeat | 接口、协议、速率、路由、目标ID | 先改姿态PID |
| 参数下载不完整 | 链路质量、其他数据流、多个GCS | 带着未知参数状态起飞 |
| 参数名不存在 | 固件版本、功能是否编入、名称迁移 | 手动创建同名参数假装支持 |
| 参数写完变回去 | 写入ACK、重启要求、脚本/其他客户端覆盖 | 重复提高写入频率 |
| Accels not healthy / inconsistent | 硬件、方向、静止状态、校准、温度 | 关闭全部IMU检查 |
| Gyros not healthy / inconsistent | 上电是否移动、异常IMU、日志 | 让飞机带故障强制解锁 |
| Compass not calibrated / inconsistent | 磁场、设备ID、安装、是否正确重启 | 在钢桌上反复校准 |
| Check mag field / offsets high | 场地磁干扰、线束/供电、校准条件 | 单纯放大阈值 |
| AHRS/EKF not ready | 等待状态、GNSS/航向源、时间与原点 | 仅凭GPS颗数够就强制飞 |
| Need position estimate | 当前模式需要定位而估计不可用 | 在室内关GPS检查飞GUIDED |
| Hardware safety switch | 实物按钮与安全状态、输出掩码 | 永久旁路安全功能 |
| Motor Emergency Stop | 实际RC逻辑值与辅助绑定 | 不查开关就反复上锁解锁 |
| RC not calibrated / failsafe | 接收机协议、端点、失联标志、RCMAP | 用固定RC覆盖掩盖断链 |
| Throttle too high | 输入校准、摇杆位置、反向和映射 | 取消油门门禁 |
| Duplicate Aux Switch Options | 重复绑定及多个开关权限 | 随机删一个不记录 |
| Battery unhealthy / low | 实际电池、监视类型、线束、比例、容量 | 把低压保护全设0 |
| Board voltage异常 | 电源、USB与外部供电、峰值负载 | 当成GPS问题反复重启 |
| Logging failed / no SD | 卡、文件系统、可用空间、写入性能 | 未留日志就开始自动调参 |
| Main loop slow / CPU负荷 | 日志配置、脚本、外设、消息负荷 | 继续增加高频采样 |
| Scripting checksum / out of memory | 实际脚本集合、堆、构建、版本 | 清掉校验或无限增大堆 |

推荐流程：记录完整原文→说明当前试验等级→最近只改变了什么→用最小系统复现→找到原因→恢复检查并重试。若重启后暂时消失，应保留“未定位原因”的状态，不把它计为修复。

| 现象 | 建议证据链 | 典型处理方向 |
|---|---|---|
| 起飞立即侧翻 | 机架图、逐电机台架记录、HUD方向 | 修正电机/桨/安装方向 |

## 61. 六个完整教学案例：先建立假设，再修改配置

下面都是**教学情境**，不表示已经在你们飞机上确认发生。

### 案例一：飞机在2.2m搜索稳定，1.3m投放总是过不了释放门禁

先看日志是高度不满足、速度不满足，还是视觉/身份问题。若姿态跟踪正常但水平速度持续约0.2m/s，检查目标是否仍在漂动、外环是否过冲、风是否太大；若height_error持续偏常量，检查本地高度参考和地面，而不是优先加垂向I。

实验拆成固定local目标悬停、视觉仅记录、视觉闭环三次。只有第三次变差，则更可能与视觉目标或时延有关。不要用放宽所有释放门禁掩盖信息质量问题。

### 案例二：开了O4之后RTK容易从Fixed掉到Float

地面保持天线位置和基站不变，只切换O4工作状态，记录rover解、供电、修正龄期。若修正龄期没变而GNSS质量变差，查射频/供电/布线；若同时MAVLink流变差，查共享电源或计算/通信负荷。

先通过改变供电路径、物理隔离或线束布置进行有记录的单变量实验，不直接把GPS过滤参数调松。任何器件供电改动先按额定参数设计。

### 案例三：QuickTune完成了，落地后没有新参数

还原开关时序：是否看到DONE？是否在仍飞行时切HIGH并看到saved？是否先LOW再HIGH？是否在保存前落地使likely_flying变false？是否其实运行的是AutoTune或QWIK？

用地面备份和日志确认，不凭界面当前一个P值判断全部参数。不同调参器的保存步骤不同，是本例的关键。

### 案例四：改成12m/s后搜桶效率反而更低

画setpoint与实际轨迹。若到区域时实际速度仍高，或者飞机需要补追和回拉，就不是“视觉识别变慢”这么简单。检查第55章的加速度、入区速度、制动距离和固定航段重启方式。

先改成经过验证的动态包络，在进入搜索区前完成减速，再比较有效覆盖和稳定桶确认时间。只看移动setpoint完成时间会低估真实用时。

### 案例五：两个舵机同时动作时飞控短暂重连

确认是否真正飞控重启、仅USB断连、GNSS单独掉电，还是MAVLink拥塞。对照上电时间、消息和电源波形/测量，检查舵机BEC、共地与回流、堵转峰值。

修复电气问题后重做全部校验；不能通过加长service timeout把飞控掉电伪装成正常慢响应。

### 案例六：第一次飞行航线正常，换场地后整体偏左

先确定“偏左”是平行平移还是角度误差随距离增长。平移更像起飞点/field偏置；距离越远越偏更像航向/场地对齐问题；只在某转弯越界则查制动和轨迹。

RTK基站位置、HOME、起飞机头方向和场地坐标都可能改变。先测量区分，不用PID去补偿场地几何错误。

## 62. 阶段实践：离线工具怎样帮助调飞控

配套压缩包中的工具全部只读取本地文本，不连接串口、网络或飞控，不发送解锁、模式、舵机和参数写入命令。它们帮助新人建立“有数据再判断”的习惯。

| 实践 | 文件 | 学习内容 |

| 参数快照与差异 | `tools/param_audit.py` | 文件格式、重复项、位掩码、版本提示 |
| 制动预算 | `tools/braking_budget.py` | 速度、加速度、延迟、轨迹可实现性 |
| 连续稳定门 | `tools/flight_metrics.py` | 时间连续性、坏帧重置、长数据空洞 |
| RTK可用性 | `tools/rtk_metrics.py` | 时间加权、修正龄期、Fixed不等于真值 |
| QuickTune数学 | `tools/quicktune_math.py` | 指数增益、回退比例、基线下限 |
| Lua只读观察 | `lua/bench_readonly_status.lua` | 参数读取、GCS文本、周期回调 |

运行方式以压缩包README为准，例如：

```bash
cd CUADC_飞控_阶段实践与记录模板
```

### 实践1：为什么不能自动“修复参数”

`ARMING_CHECK`的合法组合、输出分配和脚本使能都依赖实际硬件及任务。本工具只提示“需要人工核查”，不把警告自动变为导入文件。示例`.param`为教学数据，**不允许导入飞控**。

### 实践2：稳定0.5秒不是连续10个好点那么简单

假设20Hz采样，出现连续10个合格样本，但中间丢了1秒。按样本数判稳定会错误接受；按真实时间和最大间隔判定会重置。脚本将长空洞视为不能证明连续稳定，不做前向填充。

### 实践3：RTK统计为什么要计入没数据的时间

一段10秒日志，前1秒有Fixed，随后9秒根本没数据，不能说固定解率100%。工具明确分别报告可观测时间、未覆盖时间与整个观测窗口下的条件满足比例。

### 实践4：验证后再喂真实导出数据

CSV是本文定义的统一教学格式，不直接假装支持所有ArduPilot BIN字段。真实日志导出时先确认单位、参考坐标系、时间和传感器实例，再映射列名。工具的通过结果只是所输入数据满足教学条件，不构成起飞或投放许可。

## 64. 团队传承：每次调参必须能回答的十个问题

把每架次写成实验，而不是只保留一段“飞得不错”的视频。

1. 当前板型、固件和脚本是哪一版？
2. 飞前参数快照在哪里？
3. 当前载荷、电池、重心和机械结构是什么？
4. 本次只验证哪个假设？

7. 何时中止、谁中止、怎样恢复？
8. 新参数是否真正持久保存且重启读回一致？
9. 哪些载荷/速度/环境已经验证，哪些没有？

## 附录 A. 新飞控从开箱到基础放行：可执行的配置工作单

本附录把前文知识重新组织成操作顺序。它是**检查工作单**，不是自动设置全部参数的文件。每个阶段做完都保存快照，不越过未解释的报错。

### A.1 第一次连接前

记录实物标签、硬件修订、序列号和载板型号，拍摄线束未遮挡时的照片。检查外壳固定、SD卡、连接器、减振安装和电源极性。把所有桨取下，投放机构卸载或支撑，断开暂不需要的外设；先用最小系统确认飞控本体。

从官方渠道安装地面站及必要驱动。Windows中确认设备管理器有稳定的设备；Linux中确认对应的`/dev/serial/by-id/`链接。不要把“COM号换了”判断为固件损坏；bootloader和正常固件可能枚举不同设备。[S06](#s06)[S63](#s63)

### A.2 已有固件与空白/其他固件的处理不同

已有ArduCopter时先连接、读取完整版本、导出全参数与日志；不以升级作为排查所有问题的第一步。若确需刷写，使用**与实物板型和硬件修订匹配**的官方固件目标，按地面站指引进入加载过程。[S63](#s63)[S64](#s64)

`.apj`是常见的ArduPilot固件封装，不是参数文件。不能因为一个文件也是H7编译就强制刷给任意H7板。板型、引脚、IMU、IO MCU、存储和供电监测的定义都可能不同。[G10](#g10)

Bootloader更新、DFU恢复、自定义构建属于维护操作，通常不是普通调参步骤。遇到板ID拒绝或加载失败，应先核对型号、端口、线材与厂家说明，不删除校验强刷。自定义固件还要记录被裁掉的功能；少了Lua、某传感器驱动或日志功能，不能靠添加同名参数补出来。[S65](#s65)

刷完后重新读取版本和参数，按版本迁移说明核对重命名与单位，重新执行静态验收。恢复出厂会改变校准、输出和失效保护，不能在“恢复”后跳过配置直接带桨飞行。[S66](#s66)

### A.4 三个条件明确的串口配置例子

下面是**学习如何填写设置表**的例子。只有在端口映射与设备协议已经确认时，才根据实机参数帮助设置。示例不以`.param`形式提供，避免被误导入。

| 场景前提 | 飞控端要确认 | 对端要确认 | 验证方法 |
|---|---|---|---|
| 某V6X的TELEM1已核实为SERIAL1，接MAVLink2数传 | SERIAL1协议选择MAVLink2；该UART速率匹配机载数传UART；流控与线束一致 | 接收UART参数、空中链路和地面模块参数 | 独立读取版本/状态，加入RTCM后再次统计 |
| 某GPS1已核实为SERIAL3，接UART GNSS | SERIAL3协议选择GPS；接收机驱动与自动配置策略 | 支持的输出协议和速率；设置是否会被飞控覆盖 | GPS数据、实例、重启后配置、Fixed建立过程 |
| NUC通过USB连飞控 | USB对应接口与MAVLink配置；没有其他程序占用 | 稳定by-id路径、MAVROS FCU URL、权限 | 本地状态/odom间隔与断开后的行为 |

### A.5 CAN配置的逐层核对

先画物理总线：飞控CAN口、线缆长度、分支、终端、每个节点及供电。再核对“物理端口使用哪个驱动实例”和“该驱动使用什么协议”。最后才进入节点发现、节点固件与节点自身参数。[S32](#s32)[S33](#s33)

看到CAN节点不等于已经配置成GPS；看到GPS也不等于其罗盘或移动基线航向都正确。重启后记录设备ID与实例，尤其不要让主备GPS编号变化后沿用另一根天线的杆臂。

设备接入以后记录一份“单独正常”的基线，再把O4、机载计算机和舵机加入。只有组合时才出问题，优先怀疑共用电源、地线、资源、带宽和射频耦合，而不是反复刷接收机。

### A.6 持久化验证的标准动作

地面写参数→读回→导出快照→按要求重启→重新连接→再读回→核对实际功能。需要重启才能生效的功能，在没有重启前不以界面显示判断成功。

数传、GNSS和Lua脚本也可能有独立持久化步骤。明确“保存到谁的存储”。若只是PC软件保存了配置文件，飞控并不一定已经使用；若Lua只调用`set()`，也不等于`set_and_save()`。[S07](#s07)[G02](#g02)

<a id="appendix-b"></a>
## 附录 B. 参数阅读方法：单位、枚举、位掩码与版本迁移

### B.1 读一个参数必须读六件事

**名字、单位、值类型、适用范围、是否需重启、当前值来源。**当前值可能来自默认值、旧参数迁移、用户持久化、脚本临时改写或自动学习。参数“看起来与默认值不一样”本身不是错误。

数字枚举是一个选项编号；位掩码是多项选择；普通浮点数才通常直接代表物理量。例如`QUIK_RC_FUNC=300`不是第300个接收通道，`QUIK_AXES=3`也不是“调第三个轴”。[G02](#g02)

### B.2 位掩码亲手算一遍

若bit0表示横滚、bit1俯仰、bit2偏航，则各位权分别是1、2、4。

| 需要的轴 | 二进制 | 十进制 |
|---|---|---:|
| 横滚 | 001 | 1 |
| 俯仰 | 010 | 2 |
| 横滚+俯仰 | 011 | 3 |
| 偏航 | 100 | 4 |
| 三轴 | 111 | 7 |

“bit5”对应`1 << 5 = 32`，不是数值5。操作某个位时，不能把整个参数覆盖成32而无意清掉其他已经使用的位。对新手更合适的是地面站的逐项选框，并在写回后核对。[S56](#s56)

位编号含义必须来自该参数自己的说明。`QUIK_AXES`的bit0和`ARMING_CHECK`的bit0没有任何共同含义。

### B.3 单位换算与量纲检查

| 物理量 | 换算例子 | 常见错误 |
|---|---|---|
| 长度 | 120 cm = 1.20 m | 把厘米直接填米 |
| 速度 | 1200 cm/s = 12 m/s | 只改名字没改数值 |
| 加速度 | 300 cm/s² = 3 m/s² | 把速度值当加速度 |
| 角度 | 3000 cdeg = 30° | 把30°写成3000° |
| 角速度 | 9000 cdeg/s = 90°/s | 与rad/s混用 |
| 时间 | 33333 μs ≈ 0.033333 s | MESSAGE_INTERVAL写毫秒 |
| PWM脉宽 | 1500 μs = 1.5 ms | 当作舵机角度或频率 |

ArduCopter源码、MAVLink消息和ROS消息还可能分别使用不同坐标与单位。参数值是米，不代表所有日志字段也一定是米；数据导出工具可能已经应用了缩放。

### B.4 4.7迁移的附加对照

本表用于找到新名字，**不生成迁移文件**。名字和量纲以固定版本与读回元数据复核。[G06](#g06)[G07](#g07)[G08](#g08)

| 旧参数 | 4.7名字 | 主要变化 |
|---|---|---|
| `ATC_SLEW_YAW` | `ATC_RATE_WPY_MAX` | cdeg/s→deg/s |
| `LOIT_ACC_MAX` | `LOIT_ACC_MAX_M` | cm/s²→m/s² |
| `LOIT_BRK_ACCEL` | `LOIT_BRK_ACC_M` | cm/s²→m/s² |
| `LOIT_BRK_JERK` | `LOIT_BRK_JRK_M` | cm/s³→m/s³ |
| `PILOT_TKOFF_ALT` | `PILOT_TKO_ALT_M` | cm→m |
| `RTL_ALT_FINAL` | `RTL_ALT_FINAL_M` | cm→m |
| `RTL_CLIMB_MIN` | `RTL_CLIMB_MIN_M` | cm→m |
| `WPNAV_ACCEL_C` | `WP_ACC_CNR` | cm/s²→m/s² |
| `WPNAV_ACCEL_Z` | `WP_ACC_Z` | cm/s²→m/s² |
| `WPNAV_SPEED_UP/DN` | `WP_SPD_UP/DN` | cm/s→m/s |

官方Mission Planner迁移issue在部分ATC角加速度行写了线加速度单位；固定姿态控制源码明确是角加速度。本文据此**标明来源表述不一致**，不把它们悄悄混合成同一种物理量。主文使用的正确物理量是cdeg/s²→deg/s²。[G06](#g06)[G07](#g07)

`PSC_*`尤其不能整组乘同一个比例。迁移资料列出不同字段有不同缩放，不能仅用字符串替换实现可靠升级。本教程工具只提示名称混用，不自动转换任何参数。

### B.5 把PID数值当物理常数的误区

同样的P=0.1，在不同控制器定义、输出归一化、单位、滤波和采样条件下，可能没有可比性。不能从另一台飞机的“最佳P”直接推导自己的值。

主循环频率更高、DShot数字更大、GNSS更新更快都不自动代表闭环更好。还要看噪声、执行器带宽、延迟、资源和数据新鲜度。一个频率必须附带“谁以这个频率在做什么”。

## 附录 C. 一次完整的日志复盘工作坊

本附录假定你已经有真实BIN与飞手事件记录。没有提供实际飞行日志时，以下都是**分析步骤和假设例子**，不是对你们某次故障的诊断。

### C.1 先确认日志身份，不急着画曲线

记录文件哈希、飞机编号、固件、开始时间、电池、载荷、飞手和参数快照。确认BIN是本架次，而不是同一天上一架次；确认tlog来自正确system ID。保存原件，不在原件上截断或改写。

在Mission Planner打开DataFlash日志，查看版本/参数、模式/事件和起止时间。异常发生在起飞前、整定阶段、任务转场还是着陆？如果飞控曾重启，日志可能切成多个文件；用供电与时间证据连接，不把每个文件都视为完整任务。[S27](#s27)[S28](#s28)

### C.2 先做“事件时间线”

建立一个小表，至少标记：解锁、起飞、进入Loiter、调参开始、每轴结束、保存、切模式、载荷动作、定位质量变化、降落、上锁。Lua脚本消息与BIN中的QUIK记录可互相帮助定位，但地面无线文本可能丢失，不能要求每条文字都齐全才相信机载日志。[G02](#g02)

发现飞控模式从GUIDED变为LAND时，先找导致模式变化的原因，再分析轨迹偏离。此后位置目标可能仍被上层发布，但飞控不再按原模式跟随，不能据此说“位置环突然失效”。

### C.3 姿态与角速度配对看

在同一轴和同一时间窗口，将期望与实际叠加。先选几秒到十几秒能看清动作的窗口，再对可疑片段放大。横滚、俯仰和偏航的环绕处理不同，接近±180°的偏航误差应使用最短角差，不直接相减得到358°。

一个合理的评价顺序是：目标是否合理→延迟是否稳定→最大超调→回摆次数→收敛时间→噪声底→电机输出余量。不要在整个十分钟日志上用一条RMS替代具体事件。

“目标看起来抖”要先确认它究竟是任务位置目标、姿态目标还是角速度目标。一个离散位置阶跃经飞控内部整形后可以产生连续姿态目标；相反，20Hz更新也可能携带不连续的位置或速度变化。[S30](#s30)[G06](#g06)

### C.4 输出饱和与重心问题

对照同一时间的各电机输出、总推力估计和电池电压。某一路长期高、对侧长期低，可能对应重心偏移、桨/电机差异或控制需求；不能只看平均油门正常就排除饱和。

单瓶A1和单瓶A2分别测试能揭示非对称性。如果两种状态一侧电机都长期更高，应检查结构、推力差异或固定偏置；若偏差随载荷位置翻转，则重心与机构布局更值得优先研究。这是推理方向，需要实测支持。

记录下降、刹车和偏航时是否出现同时饱和。多旋翼的总推力、roll、pitch和yaw共享执行器能力；不能为追求yaw灵敏把其他轴余量耗尽。[G02](#g02)[G03](#g03)

### C.5 VIBE、Clipping、频谱与陷波

VIBE用于观察振动水平；Clipping计数增加意味着传感器量程边界等问题值得检查。陷波能处理某些频率的噪声，**不能还原已经裁剪丢失的测量**。[S19](#s19)

频谱检查尽量利用适当的原始/批量IMU记录或官方支持的分析链。记录配置会消耗SD带宽与计算资源，先地面确认可写，不为“更全面”无限增加采样与传感器实例。[S54](#s54)[S67](#s67)

有电机RPM时，比较峰值是否随转速移动，再选择RPM跟踪或其他适合来源。固定陷波适合什么、动态陷波适合什么由噪声证据决定。设置后要查看滤波是否覆盖实际峰值，以及姿态响应是否因为额外延迟恶化。

### C.6 EKF、GPS与RTK分层看

同时看GPS解类型、精度估计、卫星/几何、EKF相关状态与创新检验、模式事件、本地位置和速度。GNSS定位突然跳，而EKF拒绝该数据，与EKF接受跳变后local发生变化，是不同情况。[S49](#s49)

创新通常指观测与预测的不一致；大创新可能来自观测错误，也可能来自模型、时延或其他状态错误。不能只因为某个创新大，就把对应噪声参数调大让它“看起来通过”。

固定解丢失后先看修正龄期与链路计数；若修正一直正常，再考虑遮挡、共同观测、多路径、接收机角色与天线问题。若所有传感器同时短暂消失，优先寻找电源/重启/通信拥塞证据。

### C.7 AutoTune与QuickTune日志怎样看

内置AutoTune重点将整定阶段、测试目标、实际响应和最终保存对应起来；不同版本日志字段需要读当前格式。Lua QuickTune的`QUIK`记录包含脚本写入的`SRate,Gain,Param`，可观察当前轴、阶段和增益变化。[G02](#g02)[G03](#g03)

按该固定Lua算法，理想无中断增长在半对数坐标上近似直线；出现平台可能是飞手输入等待、阶段延迟、已完成或其他条件，不应立即判定“脚本挂了”。检测到边界后应有回退过程，最终持久值还要通过参数快照验证。

### C.8 如何写一条合格结论

不合格：“调了以后好多了，应该没问题。”

合格格式：“F012与F014使用同机、同类电池和同一载荷；本次仅改变经过审阅的滤波/整定候选。选取相似动作窗口后，期望—实际跟踪、输出峰值、收敛时间和电机温度的比较见表。还未验证低电量与单瓶A2，因此仅放行下一阶段，不放行全任务。”

日志统计最好保留窗口和处理参数。不同人选不同时间段、不同滤波和不同坐标定义，可能得到看似矛盾但并不互相否定的结果。

## 附录 D. 必须掌握的数学与工程估算

以下都是明确假设下的教学模型，不是无需实飞验证的性能保证。

### D.1 静态偏差、动态误差和测量噪声

静态偏差像一把整体错了刻度的尺；噪声像每次读数随机抖；动态误差像读到了过去的位置。分别对应标定、滤波与时间/系统带宽问题。把噪声滤平不会自动消除偏差；把P调大不会自动消除测量延迟。

若飞机水平速度为v、图像对应位姿延迟误差为Δt，则一阶位置误差约为`v·Δt`。在12m/s时，50ms对应0.6m；这不是说你们当前误差一定为0.6m，而是说明高速下时间问题不能忽略。

### D.2 阶跃响应四个词

**上升时间**描述从起点接近期望值的速度；**超调**描述越过目标多少；**整定时间**描述回到某误差带并保持的时间；**稳态误差**描述长期偏差。必须说明误差带和观察窗口，否则整定时间没有统一含义。

对任务投放，可能宁可慢0.3秒，也要减少来回穿越目标与图像抖动；对长距离转场，则更关注推力、加减速和航线余量。最优“手感”不等于最优任务表现。

### D.3 EMA、中值与滤波延迟

EMA可写成`y[k]=(1−α)y[k−1]+αx[k]`。α越小一般越平滑，但响应更慢。中值能抑制少数离群值，却不是消除所有错误的万能工具。若时间不一致或坐标原点错了，再复杂滤波也只是在平滑错误数据。

在频域看滤波时还应考虑相位。截止频率降低可能减少高频噪声，也可能使闭环可用带宽降低。QuickTune所需的干净测量与快速响应要共同取得平衡，而非“滤波越多越好”。[S53](#s53)

### D.4 RPM、电角转速与频率

机械转速N rpm的转频为`N/60` Hz。若某源输出电角转速，换算还与电机极对数有关。对一个有14个磁极、7极对的假设电机，电角转速与机械转速相差7倍；14是磁极数，不是極对数。

桨叶通过频率、轴转频、结构谐振及其谐波可能不同。频谱有一个峰不能直接说它就是电机转频。ESC遥测源与陷波解释必须核对量纲与极数配置。[S16](#s16)[S55](#s55)

### D.5 理想制动距离

恒定水平减速度a、忽略jerk和风：

\[
d_{brake}=\frac{v_0^2-v_1^2}{2a}
\]

如果还存在反应/通信/执行延迟τ，延迟期间近似保持v₀，则再加`v₀τ`。工程上还必须留定位误差、扰动与边界裕度。

取a=3m/s²，仅作为例子：

| 初速→末速 | 理想制动距离 | 若额外延迟0.2s |
|---|---:|---:|
| 4→0m/s | 2.67m | 3.47m |
| 6→0m/s | 6.00m | 7.20m |
| 8→0m/s | 10.67m | 12.27m |
| 12→0m/s | 24.00m | 26.40m |
| 12→6m/s | 18.00m | 20.40m |

因此，在侦察区前仅预留1.5m减速，不能在这个假设下把12m/s降到6m/s。应先改变轨迹设计，而非只提高飞控参数。

### D.6 距离短时根本到不了设定最高速度

起点终点都静止，加减速度大小均为a，速度上限v。达到v再降回0至少需要距离`v²/a`。

距离L较短时是三角速度：`v_peak=√(aL)`，`T=2√(L/a)`；较长时才有匀速段，`T=L/v+v/a`。这个模型没有jerk约束和飞控跟踪延迟，仍然只是理想参考。

L=30m、a=3m/s²、v上限12m/s，实际理想峰速约9.49m/s，静止到静止约6.32s。把30m直接除12得到2.5s，忽略了起停条件。

### D.7 v11的梯形时间规划隐含多大加速度

当最小段时间未主导时，v11有`T=L/(0.8v)`，加速段占0.2T，因此隐含`a=v/(0.2T)=4v²/L`。[P1](#p1)

对L=30m、v=12m/s，隐含a=19.2m/s²。理想定高且无阻力时，水平加速度与倾角关系是`a≈g·tanθ`，对应约63°。这说明**设置点曲线可以算出来，并不说明实际满载飞机可以跟上**。

### D.8 倾角、推力和风中的投放

定高时总推力约为`mg/cosθ`。30°需要约1.155倍重力的推力；60°需要约2倍。飞机还要留出动态、偏航与扰动控制余量。这里不包含空气阻力和其他损失。

持续侧风下，为保持位置飞机可能需要固定倾角。若这个平衡倾角超过状态机投放门限，即使控制无振荡也不能通过。应分析风和门限适用性，不让PID承担“让飞机无倾角抵抗水平风”的不可能任务。

### D.9 投掉水瓶为什么会抬头或上冲

质量下降、重心变化和转动惯量变化是三个不同效应。若释放瞬间推力来不及变化，原推力对应的`T/m`增大，可能上冲；若瓶子在侧面，原先平衡重心的力矩需求也改变。机构反作用、摆动、气压扰动又可能叠加。

无法仅由水瓶体积精确算出整机动态，因为还缺空机质量、安装位置、控制器和释放时间。把双瓶→A1单瓶、双瓶→A2单瓶分开测试，比只测试空载更有信息。

### D.10 航向误差如何变成远处横向误差

若实际场地轴与锁定的轴相差δ，沿前方L规划的点可出现约`L·sinδ`横向偏移。L=60m，δ=1°时约1.05m；δ=2°时约2.09m。

RTK厘米级定位不能自动修复错误的场地航向。这就是为什么“飞机位置准”与“路线在场地内”需要不同验收。[P1](#p1)

### D.11 Fixed时间占比与真值精度

均匀采样且不丢数据时，样本占比可以近似时间占比；若丢包很不均匀，必须按时间段统计。两个相邻样本之间很长的空洞不能无条件沿用前一个Fixed状态。

有固定解率、hAcc统计、静态散布仍不足以证明绝对误差。要验证绝对位置，需要独立且同参考系的真值；要验证投放，需要实际水瓶第一落点。不同层的“通过”不能互相替代。

### E.1 `tools/param_audit.py`

学习严格输入校验、非有限数、重复项、字典、位掩码和差异。只输出人工审阅提示，不能证明配置安全。

```python
#!/usr/bin/env python3
"""离线读取/比较参数快照；从不连接飞控、不写参数、不产生可导入配置。"""
from __future__ import annotations
import argparse
import math
import re
from pathlib import Path
from typing import Mapping

NAME = re.compile(r"^[A-Z][A-Z0-9_]{0,63}$")


def parse_params(text: str) -> dict[str, float]:
    """支持 NAME,VALUE、NAME VALUE 与 QGC 的 SYS COMP NAME VALUE TYPE。"""
    result: dict[str, float] = {}
    for line_no, raw in enumerate(text.splitlines(), 1):
        line = re.split(r"#|;|//", raw, maxsplit=1)[0].strip()
        if not line:
            continue
        fields = [v.strip() for v in line.split(",")] if "," in line else line.split()
        if len(fields) == 2:
            name, value_text = fields
        elif len(fields) == 5:
            try:
                int(fields[0]); int(fields[1]); int(fields[4])
            except ValueError as exc:
                raise ValueError(f"第{line_no}行：不是受支持的QGC五列格式") from exc
            name, value_text = fields[2], fields[3]
        else:
            raise ValueError(f"第{line_no}行：需要2列或QGC 5列，实际{len(fields)}列")
        if not NAME.fullmatch(name):
            raise ValueError(f"第{line_no}行：无效参数名 {name!r}")
        if name in result:
            raise ValueError(f"第{line_no}行：重复参数 {name}，拒绝静默覆盖")
        try:
            value = float(value_text)
        except ValueError as exc:
            raise ValueError(f"第{line_no}行：{name}不是数值") from exc
        if not math.isfinite(value):
            raise ValueError(f"第{line_no}行：{name}非有限值")
        result[name] = value
    if not result:
        raise ValueError("参数文件没有有效参数")
    return result


def int_field(name: str, value: float) -> int:
    if not math.isfinite(value) or not float(value).is_integer() or value < 0:
        raise ValueError(f"{name}应为非负整数，实际{value}")
    return int(value)


def audit(params: Mapping[str, float], family: str | None = None) -> list[str]:
    notes: list[str] = []
    if "ARMING_CHECK" in params:
        value = int_field("ARMING_CHECK", params["ARMING_CHECK"])
        if value & 1 == 0:
            notes.append("旧版ARMING_CHECK未选择All位：核查被省略的检查，不能自动判为安全")
    if "ARMING_SKIPCHK" in params:
        value = int_field("ARMING_SKIPCHK", params["ARMING_SKIPCHK"])
        if value != 0:
            notes.append("新版ARMING_SKIPCHK非0：存在跳过检查的位，逐项审阅")
    if "ARMING_CHECK" in params and "ARMING_SKIPCHK" in params:
        notes.append("同时出现新旧解锁检查名称：核查快照来源/版本，禁止按数值互换")
    if not any(p in params for p in ("ARMING_CHECK", "ARMING_SKIPCHK")):
        notes.append("快照缺解锁检查字段：这是信息不足，不是检查已通过")
    for index in (9, 10):
        key = f"SERVO{index}_FUNCTION"
        if key not in params:
            notes.append(f"缺少{key}：无法确认v11投放输出用途")
        elif params[key] != 0:
            notes.append(f"{key}={params[key]:g}：必须核对输出用途及DO_SET_SERVO兼容性，不自动修改")
    bindings: dict[int, list[str]] = {}
    for name, value in params.items():
        if re.fullmatch(r"RC\d+_OPTION", name):
            func = int_field(name, value)
            if func:
                bindings.setdefault(func, []).append(name)
    for func, names in bindings.items():
        if len(names) > 1:
            notes.append(f"辅助功能{func}重复绑定{', '.join(sorted(names))}：核查是否有意及是否冲突")
    if params.get("QUIK_ENABLE", 0) > 0 and params.get("QWIK_ENABLE", 0) > 0:
        notes.append("QUIK与QWIK同时使能：检查是否误启两种调参器；快照不能证明实际脚本已加载")
    if params.get("QUIK_ENABLE", 0) > 0:
        notes.append("QUIK处于使能状态：比赛前核对脚本/RC；固定Lua中ENABLE=0不等于空中回退")
    if family == "4.7" and any(k in params for k in ("WPNAV_SPEED", "ANGLE_MAX", "LAND_SPEED")):
        notes.append("声明4.7但含旧导航/角度参数名：核对实际固件及迁移，不自动换算")
    if family in ("4.5", "4.6") and any(k in params for k in ("WP_SPD", "ATC_ANGLE_MAX", "LAND_SPD_MS")):
        notes.append("声明旧版本但含4.7名称：核查快照，不把新单位填进旧参数")
    if family is None:
        notes.append("未指定固件系列：不推断单位；名称不是可靠的完整固件版本证据")
    return notes


def differences(before: Mapping[str, float], after: Mapping[str, float]) -> list[str]:
    out: list[str] = []
    for name in sorted(set(before) | set(after)):
        if name not in before:
            out.append(f"ADDED   {name}: {after[name]:.9g}")
        elif name not in after:
            out.append(f"REMOVED {name}: {before[name]:.9g}")
        elif before[name] != after[name]:
            out.append(f"CHANGED {name}: {before[name]:.9g} -> {after[name]:.9g}")
    return out


def main() -> None:
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument("snapshot", type=Path)
    parser.add_argument("--compare", type=Path)
    parser.add_argument("--family", choices=("4.5", "4.6", "4.7"))
    args = parser.parse_args()
    try:
        before = parse_params(args.snapshot.read_text(encoding="utf-8-sig"))
        print("只读审阅；没有警告不代表可安全飞行；不自动修改任何配置。")
        print(f"快照参数数：{len(before)}")
        for note in audit(before, args.family):
            print("CHECK:", note)
        if args.compare:
            after = parse_params(args.compare.read_text(encoding="utf-8-sig"))
            print("\n参数差异（精确数值比较）：")
            print("\n".join(differences(before, after)) or "无数值差异")
            print("\n后快照审阅：")
            for note in audit(after, args.family):
                print("CHECK:", note)
    except (OSError, UnicodeError, ValueError) as exc:
        parser.exit(2, f"输入错误：{exc}\n")


if __name__ == "__main__":
    main()
```

### E.2 `tools/braking_budget.py`

学习速度/加速度量纲、制动与静止起停模型，并计算v11时间分配隐含的加速度。

```python
#!/usr/bin/env python3
"""离线理想制动/轨迹算例；不是实机可飞性验证或飞行参数生成器。"""
from __future__ import annotations
import argparse
import math


def finite(value: float, name: str, positive: bool = False) -> float:
    if not math.isfinite(value) or value < 0 or (positive and value == 0):
        raise ValueError(f"{name}必须为有限{'正' if positive else '非负'}数")
    return value


def stopping_distance(speed: float, accel: float, latency: float = 0.0,
                      end_speed: float = 0.0) -> float:
    for value, name in ((speed, "speed"), (latency, "latency"), (end_speed, "end_speed")):
        finite(value, name)
    finite(accel, "accel", True)
    if end_speed > speed:
        raise ValueError("末速度大于初速度，不是制动过程")
    return speed * latency + (speed * speed - end_speed * end_speed) / (2.0 * accel)


def rest_to_rest(distance: float, speed_limit: float, accel: float) -> tuple[float, float]:
    finite(distance, "distance")
    finite(speed_limit, "speed_limit", True)
    finite(accel, "accel", True)
    if distance <= speed_limit * speed_limit / accel:
        peak = math.sqrt(distance * accel)
        return 2.0 * peak / accel, peak
    return distance / speed_limit + speed_limit / accel, speed_limit


def v11_profile(distance: float, speed_limit: float, min_time: float = 1.0) -> tuple[float, float, float]:
    """按v11时间分配推导：返回时长、真实setpoint峰速、隐含加速度。"""
    finite(distance, "distance")
    finite(speed_limit, "speed_limit", True)
    finite(min_time, "min_time", True)
    duration = max(min_time, distance / (0.8 * speed_limit))
    peak = distance / (0.8 * duration)
    return duration, peak, peak / (0.2 * duration)


def main() -> None:
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument("--distance", type=float, required=True)
    parser.add_argument("--speed", type=float, required=True)
    parser.add_argument("--accel", type=float, required=True)
    parser.add_argument("--latency", type=float, default=0.0)
    parser.add_argument("--end-speed", type=float, default=0.0)
    args = parser.parse_args()
    try:
        d = stopping_distance(args.speed, args.accel, args.latency, args.end_speed)
        duration, peak = rest_to_rest(args.distance, args.speed, args.accel)
        old_t, old_v, old_a = v11_profile(args.distance, args.speed)
```

### E.3 `tools/csv_common.py`

两种CSV分析的公共输入层。先拒绝错误结构和时间，再计算统计，避免把坏数据平均成好结果。

```python
"""只读、严格的统一教学CSV解析，不猜测BIN原始字段。"""
from __future__ import annotations
import csv
import math
from pathlib import Path
from typing import Iterable


def read_numeric_csv(path: Path, columns: Iterable[str]) -> list[dict[str, float]]:
    required = set(columns)
    rows: list[dict[str, float]] = []
    with path.open(encoding="utf-8-sig", newline="") as stream:
        reader = csv.DictReader(stream)
        if reader.fieldnames is None:
            raise ValueError("CSV没有表头")
        if len(reader.fieldnames) != len(set(reader.fieldnames)):
            raise ValueError("CSV有重复列名")
        if not required.issubset(reader.fieldnames):
            raise ValueError(f"CSV缺少列：{sorted(required - set(reader.fieldnames))}")
        for number, raw in enumerate(reader, 2):
            if None in raw:
                raise ValueError(f"CSV第{number}行：列数过多")
            parsed: dict[str, float] = {}
            for key in required:
                try:
                    value = float(raw[key])
                except (TypeError, ValueError) as exc:
                    raise ValueError(f"CSV第{number}行：{key}缺失或非数值") from exc
                if not math.isfinite(value):
                    raise ValueError(f"CSV第{number}行：{key}非有限值")
                parsed[key] = value
            if parsed.get("time_s", 0.0) < 0:
                raise ValueError(f"CSV第{number}行：时间不能为负")
            if rows and "time_s" in parsed and parsed["time_s"] <= rows[-1]["time_s"]:
                raise ValueError(f"CSV第{number}行：时间必须严格递增，不接受重复/倒退")
            rows.append(parsed)
    if len(rows) < 2:
        raise ValueError("至少需要两个样本，不能从一个点证明连续性")
    return rows
```

### E.4 `tools/flight_metrics.py`

按统一教学列统计连续好样本跨度。离散观测之间不能证明持续满足，长间隔重置；max_gap不是v11原始参数。

```python
#!/usr/bin/env python3
"""统一CSV中的投放条件离线统计；不能作为飞行/投放放行器。"""
from __future__ import annotations
import argparse
import json
import math
from dataclasses import dataclass
from pathlib import Path
from csv_common import read_numeric_csv

COLUMNS = (
    "time_s", "identity_ok", "area_ok", "center_err_m", "outlet_err_m",
    "predicted_err_m", "height_err_m", "hspeed_mps", "vz_mps",
    "roll_deg", "pitch_deg", "omega_dps",
)

@dataclass(frozen=True)
class Limits:
    center: float = 0.35
    outlet: float = 0.20
    height: float = 0.15
    hspeed: float = 0.15
    vz: float = 0.10
    angle: float = 8.0
    omega: float = 10.0
    stable_s: float = 0.50
    max_gap_s: float = 0.15  # 教学连续性阈值，不是原v11的全局odom超时


def row_valid(row: dict[str, float], limits: Limits) -> bool:
    for name in ("identity_ok", "area_ok"):
        if row[name] not in (0.0, 1.0):
            raise ValueError(f"{name}只能用0/1，不猜测其他状态")
    for name in ("center_err_m", "outlet_err_m", "predicted_err_m", "height_err_m", "hspeed_mps", "omega_dps"):
        if row[name] < 0:
            raise ValueError(f"{name}不能为负；先确认单位和导出方法")
    return (
        row["identity_ok"] == 1 and row["area_ok"] == 1
        and row["center_err_m"] <= limits.center
        and row["outlet_err_m"] <= limits.outlet
        and row["predicted_err_m"] <= limits.outlet
        and row["height_err_m"] <= limits.height
        and row["hspeed_mps"] <= limits.hspeed
        and abs(row["vz_mps"]) <= limits.vz
        and abs(row["roll_deg"]) <= limits.angle
        and abs(row["pitch_deg"]) <= limits.angle
        and row["omega_dps"] <= limits.omega
    )


def evaluate(rows: list[dict[str, float]], limits: Limits = Limits()) -> dict[str, float | int | bool]:
    if len(rows) < 2:
        raise ValueError("至少需要两个样本")
    if any(not math.isfinite(v) or v <= 0 for v in vars(limits).values()):
        raise ValueError("所有教学阈值必须是有限正数")
    start: float | None = None
    previous_t: float | None = None
    previous_good = False
    longest = 0.0
    good_count = 0
    gap_count = 0
    for row in rows:
        if any(key not in row or not math.isfinite(row[key]) for key in COLUMNS):
            raise ValueError("行中存在缺失或非有限字段")
        t = row["time_s"]
        if t < 0 or (previous_t is not None and t <= previous_t):
            raise ValueError("time_s必须非负且严格递增")
        dt = None if previous_t is None else t - previous_t
        large_gap = dt is not None and dt > limits.max_gap_s
        if large_gap:
            gap_count += 1
        good = row_valid(row, limits)
        if good:
            good_count += 1
            if start is None or not previous_good or large_gap:
                start = t
            longest = max(longest, t - start)
        else:
            start = None
        previous_t, previous_good = t, good
    return {
        "samples": len(rows), "good_samples": good_count,
        "large_gaps": gap_count, "longest_observed_good_span_s": longest,
        "meets_demo_dwell": longest + 1e-12 >= limits.stable_s,
    }


def main() -> None:
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument("csv", type=Path)
    parser.add_argument("--max-gap", type=float, default=0.15)
    args = parser.parse_args()
    try:
        result = evaluate(read_numeric_csv(args.csv, COLUMNS), Limits(max_gap_s=args.max_gap))
    except (OSError, UnicodeError, ValueError) as exc:
        parser.exit(2, f"输入错误：{exc}\n")
    print("仅输入CSV的教学统计；离散样本不证明采样间行为，也不证明物理释放。")
    print(json.dumps(result, ensure_ascii=False, indent=2))


if __name__ == "__main__":
    main()
```

### E.5 `tools/rtk_metrics.py`

区分整个观测窗口、可覆盖区间、数据空洞与两端满足Fixed/龄期条件的区间。不是绝对精度评估。

```python
#!/usr/bin/env python3
"""只读RTK CSV统计；Fixed和hAcc不是独立真值精度证明。"""
from __future__ import annotations
import argparse
import json
import math
from pathlib import Path
from csv_common import read_numeric_csv

COLUMNS = ("time_s", "fix_type", "rtcm_age_s", "hacc_m")


def evaluate(rows: list[dict[str, float]], max_gap_s: float = 2.0,
             max_age_s: float = 2.0, max_hacc_m: float = 0.10) -> dict[str, float | int]:
    if len(rows) < 2:
        raise ValueError("至少需要两个样本")
    if any(not math.isfinite(v) or v <= 0 for v in (max_gap_s, max_age_s, max_hacc_m)):
        raise ValueError("阈值必须为有限正数")
    for index, row in enumerate(rows):
        if any(key not in row or not math.isfinite(row[key]) for key in COLUMNS):
            raise ValueError("缺少字段或存在非有限数据")
        if row["time_s"] < 0 or row["rtcm_age_s"] < 0 or row["hacc_m"] <= 0:
            raise ValueError("时间/龄期须非负，hAcc须正值；未知值不能填0伪装精确")
        if row["fix_type"] < 0 or not float(row["fix_type"]).is_integer():
            raise ValueError("fix_type须非负整数，常见MAVLink RTK Fixed为6")
        if index and row["time_s"] <= rows[index - 1]["time_s"]:
            raise ValueError("time_s必须严格递增")
    span = rows[-1]["time_s"] - rows[0]["time_s"]
    covered = fixed = qualified = 0.0
    gaps = 0
    for before, after in zip(rows, rows[1:]):
        dt = after["time_s"] - before["time_s"]
        if dt > max_gap_s:
            gaps += 1
            continue
        covered += dt
        if before["fix_type"] == after["fix_type"] == 6:
            fixed += dt
            if (before["rtcm_age_s"] <= max_age_s and after["rtcm_age_s"] <= max_age_s
                and before["hacc_m"] <= max_hacc_m and after["hacc_m"] <= max_hacc_m):
                qualified += dt
    return {
        "samples": len(rows), "window_s": span, "covered_intervals_s": covered,
        "uncovered_s": max(0.0, span - covered), "large_gaps": gaps,
        "both_endpoints_fixed_s": fixed,
        "both_endpoints_qualified_s": qualified,
        "fixed_intervals_over_whole_window_pct": 100.0 * fixed / span,
        "qualified_intervals_over_whole_window_pct": 100.0 * qualified / span,
    }


def main() -> None:
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument("csv", type=Path)
    parser.add_argument("--max-gap", type=float, default=2.0)
    parser.add_argument("--max-age", type=float, default=2.0)
    parser.add_argument("--max-hacc", type=float, default=0.10)
    args = parser.parse_args()
    try:
        result = evaluate(read_numeric_csv(args.csv, COLUMNS), args.max_gap, args.max_age, args.max_hacc)
    except (OSError, UnicodeError, ValueError) as exc:
        parser.exit(2, f"输入错误：{exc}\n")
    print("教学阈值，不是ArduPilot默认准入标准；只计短间隔两端都满足的区间。")
    print(json.dumps(result, ensure_ascii=False, indent=2))


if __name__ == "__main__":
    main()
```

### E.6 `tools/quicktune_math.py`

只计算指数增益增长和振荡分支的简化回退限制；没有执行整定，没有模拟真实振荡，也不处理全部源码分支。

```python
#!/usr/bin/env python3
"""简化单参数QuickTune数学练习，无Lua上传、无飞控连接、无写参数。"""
from __future__ import annotations
import argparse
import math


def multiplier(rate_hz: float = 40.0, double_time_s: float = 10.0) -> float:
    if any(not math.isfinite(v) or v <= 0 for v in (rate_hz, double_time_s)):
        raise ValueError("频率与翻倍时间必须是有限正数")
    exponent = math.log(2.0) / rate_hz / double_time_s
    if exponent > 700:
        raise ValueError("输入导致不合理的指数溢出")
    return math.exp(exponent)


def backed_off(initial: float, detected: float, gain_margin: float = 60.0,
               max_reduce: float = 20.0) -> tuple[float, float, float]:
    if not math.isfinite(initial) or initial <= 0:
        raise ValueError("初值须有限且大于0")
    if not math.isfinite(detected) or detected < 0:
        raise ValueError("检测值须有限且非负")
    if any(not math.isfinite(v) or not 0 <= v <= 100 for v in (gain_margin, max_reduce)):
        raise ValueError("比例必须在0至100之间")
    raw = detected * (1.0 - gain_margin / 100.0)
    floor = initial * (1.0 - max_reduce / 100.0)
    return raw, floor, max(raw, floor)


def main() -> None:
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument("--initial", type=float, required=True)
    parser.add_argument("--detected", type=float, required=True)
    parser.add_argument("--margin", type=float, default=60.0)
    parser.add_argument("--max-reduce", type=float, default=20.0)
    parser.add_argument("--double-time", type=float, default=10.0)
    args = parser.parse_args()
    try:
        m = multiplier(40.0, args.double_time)
        raw, floor, final = backed_off(args.initial, args.detected, args.margin, args.max_reduce)
    except ValueError as exc:
        parser.error(str(exc))
    print("仅演示振荡分支的简化数学；未模拟yaw上限、联动P/I、保护与实际振荡。")
    print(f"40Hz名义每步倍率={m:.9f}")
    print(f"回退计划={raw:.6f}，初始基线下限={floor:.6f}，受限结果={final:.6f}")


if __name__ == "__main__":
    main()
```

<a id="appendix-g"></a>
## 附录 G. 30个阶段性练习与参考答案

先独立回答，再看答案。答案不替代实物针脚图、对应固件元数据与试飞记录。

### G.1 基础配置

**1．飞控有电、HUD正常，但所有舵机不动，先查PID吗？**

不查。先检查舵机电源、公共信号参考、输出安全状态、FUNCTION、物理输出映射、协议分组和指令是否到达。USB供电不意味着舵机电源轨已经供电。

**2．电机测试按钮A驱动了某电机，能直接认定它是Motor1吗？**

不能。测试字母与机架图中的测试顺序相关，必须对照当前frame定义和SERVO功能映射，无桨逐个核对物理位置和旋向。

**3．同型号飞控能否互相导入完整参数？**

不能默认安全。校准、设备ID、输出、接收机、电源、机体和外参可能不同。用对照表迁移可迁移的设计意图，重新校准与验收。

**4．为什么关掉所有PreArm检查不是“修好了解锁失败”？**

它消除了拒绝信号，没有消除被检测到的故障。下一步飞行仍可能面对错误姿态、电源、定位或执行器状态。

**5．一份4.6教程写WPNAV_SPEED=1200，把1200写进4.7的WP_SPD有什么问题？**

单位从cm/s改成m/s；物理意义差100倍。应先核对对应版本。即使数值超范围被拒绝，也不能依赖拒绝来防止全部迁移错误。

### G.2 通信与RTK

**6．115200 UART是否意味着115200 byte/s？**

不是。按8N1理想计算约11520 byte/s，实际还要考虑协议、无线调度、队列和重传。

**7．串口波特率正确、MAVLink仍不通，接着查什么？**

电平和TX/RX/GND、物理端口到SERIAL映射、协议、流控、串口占用、设备是否真的发数据，以及路由/系统ID。不能只反复换波特率。

**8．O4清楚而地面站卡顿，说明飞控CPU一定不够吗？**

不能。它们可能走不同链路。先检查MAVLink吞吐、RTCM竞争、射频干扰和供电，再检查调度/CPU证据。

**9．有两个GNSS接口，就能不用罗盘获得航向吗？**

不能。需要支持移动基线航向的设备、正确角色和链路、已知刚性基线及EKF源配置。

**10．同一个地面点三次RTK Fixed都很集中，就证明绝对误差2cm吗？**

只能说明在所用条件下重复性好；仍需独立真值、参考系和基站坐标证据才能评价绝对误差。

**11．基站Survey-in通过，却一直Float，如何缩小范围？**

分开确认有效RTCM产生、发送、飞控收到、rover收到并使用、共同星座/观测、修正龄期及接收机配置。Survey通过只覆盖第一部分。

**12．NAV30平均30Hz，为什么视觉仍无法插值？**

平均值掩盖长间隔；也可能时钟域、时间戳、顺序和队列不匹配。v11需要相应时刻的两个odom样本满足间隔条件，不仅要求平均率。

### G.3 控制与自动调参

**13．姿态跟踪很好，但飞机沿桶周围绕圈，应先增加D吗？**

先查航向、定位、坐标变换、上层目标和外环。没有证据表明角速度环阻尼不足，就不应先改D。

**14．为什么机械振动应先于AutoTune处理？**

辨识过程依赖有效测量；振动、裁剪与噪声会污染判断。滤波也不能还原已经丢失的数据。

**15．Lua QuickTune的GAIN_MARGIN=60表示保留60%吗？**

不是。检测到振荡时计划减少60%、保留40%，还要经过基线最大降低、yaw上限等约束。

**16．初始P=0.10、振荡点0.12，回退60%、最大降低20%，教学约束结果是多少？**

计划0.048；初始基线下限0.08；在没有其他限制的该算例中结果为0.08。

**17．DOUBLE_TIME=10，20秒无暂停理想增长到几倍？**

4倍。它是指数增长，不是每10秒加同一固定数值；实际脚本有阶段、上下界和暂停条件。

**18．QUIK_ANGLE_MAX=10是否禁止飞机任何时候倾斜超过10°？**

不是。该脚本检查目标姿态与实际姿态的误差角。飞机能以更大目标倾角飞而误差仍小；任务RELEASE的绝对roll/pitch门限是另一项。

**19．Lua整定中动摇杆，是否立刻回到原PID？**

该固定源码仅据此暂停继续整定并等待约4秒，不能认定全部参数自动恢复。应按专用LOW中止流程处理需要回退的情况。

**20．Lua出现DONE，落地上锁后参数消失，可能是什么？**

没有按Lua流程在落地前切HIGH保存。不要把内置AutoTune接受后落地保存的路径套过来。

**21．为什么QUIK_ENABLE=0不是可靠的空中回退按钮？**

固定源码在ENABLE分支直接返回，可能还没有运行恢复旧参数分支。已经写入RAM的候选增益可能保留。

**22．pcall成功捕获异常后，参数事务是否自动撤销？**

不会。pcall不是数据库事务；这份wrapper记录错误并安排重试，没有统一撤销此前改动。

**23．只调roll/pitch却看到yaw SMAX变化，是不是一定串轴？**

不一定。固定Lua的setup_SMAX遍历所有轴，为没有设置SMAX的轴补默认值。要读源码和差异，而非只看AXES推断写入范围。

**24．QWIK和QUIK只有拼写不同吗？**

不是。对应内置C++与Lua机制，参数名、默认值、禁用/模式保护都有实际差异。不能互相套用保证，也不要同时运行。

### G.4 任务验收

**25．12m/s、3m/s²减速到0，忽略其他因素需要几米？**

24m；若先有0.2s延迟，增加2.4m，合26.4m；还没加工程安全裕度。

**26．30m静止到静止、速度上限12m/s、a=3m/s²，能全程12m/s吗？**

不能。理想峰速约9.49m/s，总时间约6.32s，尚未计jerk和实际跟踪。

**27．连续10个20Hz好样本一定代表稳定0.5秒吗？**

相邻规则间隔下，第1到第10只跨0.45秒；若中间还有数据空洞，更不能按样本数证明连续稳定。

**28．水平速度很低、出瓶口几何误差很小，就能证明命中桶吗？**

不能。还有测量偏差、机构延迟、瓶子运动、风、桶口几何与实际第一落点。几何门限是允许动作条件的一部分。

**29．空载整定很好，双瓶和单瓶还要测什么？**

推力余量、输出饱和、重心偏移、结构摆动、释放瞬态、垂向恢复、低电量行为；单瓶A1/A2分别验证。

**30．任务进程死了但MAVROS仍发心跳，GCS失联保护一定会触发吗？**

不能保证。还要看心跳来源、飞控识别的系统、协议路由和其他发送者。应验证setpoint新鲜度与任务进程健康，而非只依赖连接图标。

### G.5 综合作业

提交一个不含真机控制指令的“飞控放行资料夹”：完整身份表、端口图、参数差异报告、RTK数据统计、一次调参操作流程选择题、12m/s制动预算、失效保护矩阵和未验证清单。

评分重点是证据与推理是否一致，不是参数列表是否长。对无法确定的字段明确写“未知、待实测”，比填入另一台飞机的数字更合格。

### I.1 三份参数分别在哪里

飞控PID、滤波、串口、EKF与失效保护在飞控；任务速度、状态机时间和几何门限在C++/ROS参数；相机内外参、模型阈值和视觉时间戳在视觉链。修改其中一份，不应假定另两份自动同步。

### I.2 看懂一次RELEASE等待

先读`Direct release waiting`的字段，再找对应测量与来源。速度不满足可来自飞控运动或速度坐标理解；姿态不满足可来自风、指令或控制；几何不满足可来自外参、视觉、位置和姿态共同作用。按这条证据链查，不先拍脑袋选一个PID。

### I.3 上锁判据的边界

v11没有把ExtendedState作为最终触地凭据，而使用相对高度和速度连续确认。这是特定项目选择，不保证对所有地面高差、EKF漂移和传感器异常都安全；飞控实际落地检测、任务程序判断与真实接地仍应分别验证。不要为了让程序退出而在空中强制上锁。

## 附录 J. 术语速查：从报错到正确的系统层

| 术语 | 中文理解 | CUADC中容易混淆的地方 |
|---|---|---|
| Autopilot hardware | 飞控硬件 | CUAV型号不是固件版本 |
| ArduCopter | 多旋翼/直升机固件 | 不与Plane固件流程混用 |
| Firmware target | 固件编译目标 | 同MCU不等于同板型 |
| Bootloader | 引导加载程序 | 不需要每次调参都升级 |
| Ground station / GCS | 地面站 | 能连上不代表所有链路健康 |
| MAVLink | 消息协议 | 不是物理串口也不是无线模块 |
| MAVROS | ROS与MAVLink接口 | ROS参数不是飞控参数 |
| Companion computer | 伴随计算机 | 进程退出不等于飞控掉电 |
| Armed / Disarmed | 解锁/上锁 | 不能凭高度一个量判断安全上锁 |
| Safety switch | 输出安全按钮/状态 | 不等于带载物理断电 |
| Emergency stop | 紧急停止功能 | 与模式切换、正常降落不同 |
| PreArm | 解锁前检查 | 消除提示与消除根因不同 |
| Failsafe | 失效保护 | 多层保护可能有相互影响 |
| Frame class/type | 机架类别/布局 | 决定混控与电机关系 |
| Motor test | 电机测试 | 字母与逻辑Motor号需要对照 |
| SERVO output | 逻辑执行器输出 | 不与同号RC输入绑定 |
| PWM | 脉宽调制输出 | 脉宽、频率、电压是不同量 |
| DShot | 数字ESC控制协议 | 不是所有输出组都支持相同模式 |
| ESC telemetry | 电调遥测 | 与双向DShot的关系依方案而定 |
| BEC | 稳压供电模块 | 检查峰值、电压与反向供电 |
| Brownout | 供电掉压导致异常 | 常伪装成通信/传感器故障 |
| IMU | 惯性测量单元 | 不直接提供绝对位置 |
| Gyroscope | 陀螺仪 | 测角速度，不是直接测航向 |
| Accelerometer | 加速度计 | 原始比力不等于世界系运动加速度 |
| Magnetometer | 磁力计/罗盘 | 电流干扰可随油门变化 |
| Barometer | 气压计 | 受压力、气流和环境影响 |
| AHRS | 姿态航向估计系统 | 不是单独某一个罗盘 |
| EKF | 扩展卡尔曼滤波器 | 源选择、时延、创新都需合理 |
| Innovation | 观测与预测的不一致 | 大创新不必然是观测传感器坏 |
| Lane switch / reset | 融合实例切换/状态重置 | 可能影响任务冻结的local坐标 |
| GNSS | 全球导航卫星系统 | 不只有GPS一个星座 |
| DOP | 精度稀释因子 | 不能直接读成米 |
| hAcc / vAcc | 水平/垂直精度估计 | 不是独立真值误差 |
| RTK Float | RTK浮点解 | 不是修正必然完全断开 |
| RTK Fixed | RTK固定解 | 不保证罗盘和EKF正常 |
| Survey-in | 基站自主测定过程 | 不等于测量级已知坐标 |
| RTCM | GNSS修正消息格式 | 不等于UBX定位输出 |
| NTRIP caster | 修正数据分发服务 | 网络连接成功不等于收到有效RTCM |
| Mountpoint | 修正流入口名称 | 需匹配服务、位置与接收机能力 |
| GGA | 常用位置报告语句 | 部分网络修正服务需要 |
| Moving baseline | 移动基线 | 常用于机载双天线航向 |
| Lever arm | 杆臂/安装偏移 | 天线、IMU、相机、投放口各自不同 |
| FRD / FLU | 前右下/前左上 | y、z符号不同 |
| NED / ENU | 北东地/东北天 | 不能只翻转一个z就完成全部变换 |
| PID / FF | 比例积分微分/前馈 | 内环、外环与单位要区分 |
| Saturation | 输出饱和 | 改PID不能增加硬件最大推力 |
| Notch filter | 陷波滤波 | 不修复传感器裁剪或线束松动 |
| Harmonic | 谐波 | 基频和倍频要靠证据定位 |
| Slew rate | 变化率类指标 | QuickTune指标不等于陀螺角速度 |
| AutoTune | 内置自动整定 | 完成、试用、保存是不同事件 |
| QUIK / QWIK | Lua/C++ QuickTune前缀 | 默认值和保护行为不完全相同 |
| Setpoint | 控制目标/设置点 | 目标速度不等于真实速度 |
| Jerk | 加速度变化率 | 速度与加速度连续还不一定平滑 |
| Dwell | 连续保持时间 | 不应只数好样本个数 |
| ACK | 命令响应/确认 | 不代表机械动作或真实落点已完成 |
| BIN / tlog / bag | 机载/链路/ROS日志 | 数据覆盖和时钟不同 |
| FMT / UNIT | 日志格式/单位描述 | 导出前先确认缩放 |
| Checksum / hash | 校验/内容指纹 | 标识一致不等于行为已验证 |
| Envelope | 已验证工作包络 | 载荷、速度、环境、电池共同限定 |

读到一个报错时，先在这张表中找它属于哪个层，再选择对应检查。不要把所有异常都塞进“调PID”这一个动作。
